## Overall Assessment

The accepted persisted-artwork architecture is coherent at the high level:

`Arr metadata -> canonical match/metadata -> asynchronous renderer -> supported Jellyfin item-image API -> normal Jellyfin image routes`

The previous image-interception decision is not reopened. The remaining issues are new V1 contract gaps around provenance, matching, scope, and recovery.

The repository is **not yet ready for full V1 implementation**. A foundation-only spike could begin, but provider, matching, and artwork implementation should wait for the blocker and pre-implementation items below.

## BLOCKER

### 1. Provenance Cannot Prove Artwork Ownership

`PublishedArtworkState` contains an optional `sourceReference`, source fingerprint, and published fingerprint, but no defined retained-source artifact, active-image identity, publication token, or comparison algorithm.

References:

- `docs/data-model.md:397-413`
- `docs/architecture.md:180-197`
- `docs/decisions.md:32-39`

Before replacing a poster, the plugin must be able to determine:

- Which source artwork was captured.
- Which active image was generated by ArrTags.
- Whether the current active image is still ArrTags-owned.
- Whether a later manual or provider image replaced it.
- Whether restoration is safe.

Without this, disabling or uninstalling ArrTags can either fail to restore the original or overwrite a user’s later artwork.

### 2. Publication and Provenance Are Not Crash-Consistent

The current flow performs separate operations:

1. Capture or identify source artwork.
2. Render derived artwork.
3. Call `SaveImage`.
4. Update Jellyfin item state.
5. Persist ArrTags provenance.

The documentation does not define recovery if the process stops between these operations.

References:

- `docs/architecture.md:256-271`
- `docs/architecture.md:331-346`
- `docs/data-model.md:732-766`
- `PLANS.md:333-358`

A crash could leave:

- A derived active image without recoverable source provenance.
- Provenance pointing to an image that was not published.
- An orphaned source or artwork artifact.
- Unsafe restoration state after restart.

A versioned publication state machine and restart reconciliation protocol are required before artwork publication code begins.

## PRE-IMPLEMENTATION

### Architecture and Documentation

- `docs/architecture.md:449-490` contains a second, older architecture section with a separate phase plan. It conflicts with the current `PLANS.md` milestone structure and should be removed or explicitly marked historical.
- `docs/jellyfin-12-architecture.md:289-312` still presents the alternatives without clearly linking the accepted ADR. The research classification is valid, but the selected decision should be explicitly cross-referenced.
- `docs/media-metadata-mapping.md:5-15` says it does not mandate matching order and excludes reverse provider-to-Jellyfin lookup, while the architecture depends on both matching order and webhook resolution.
- `README.md` is empty. This is not a coding blocker, but supported versions, active-artwork behavior, restoration limits, and Enhanced behavior must be documented before release.

### Canonical Matching Model

`MediaMatch.externalRecordId` is singular, but a Sonarr episode requires at least:

- Sonarr series ID.
- Sonarr episode ID.
- Current episode-file ID.

References:

- `docs/data-model.md:235-254`
- `docs/data-model.md:479-520`
- `docs/sonarr-api.md:133-141`

The canonical model should explicitly represent the series/episode relationship rather than relying on an ambiguous singular field or an opaque extension.

### V1 Item and File Scope

The plan and model still include unresolved behavior for:

- Series and season posters.
- Aggregate quality semantics.
- Indexed images.
- Alternate versions.
- Stacked parts.
- Specials.
- Anime/absolute numbering.
- Double episodes.
- Multi-episode files.

References:

- `PLANS.md:170-181`
- `PLANS.md:414-422`
- `docs/media-metadata-mapping.md:295-321`
- `docs/media-metadata-mapping.md:455-473`

V1 needs an explicit conservative policy, such as movie and episode primary posters only, with no badge when a single source cannot be proven.

### Multiple Arr Connections

The architecture supports multiple connections, but does not define:

- Connection-to-library mapping.
- Precedence between multiple instances.
- Ambiguity behavior when two instances contain the same item.
- Whether V1 permits only one Sonarr and one Radarr connection.

References:

- `docs/architecture.md:160-168`
- `docs/data-model.md:436-452`
- `docs/media-metadata-mapping.md:270-273`

### Provider Catalogue and Normalization

Sonarr fallback matching requires a cached catalogue, but no catalogue cache or refresh strategy is defined.

References:

- `docs/architecture.md:216-220`
- `docs/sonarr-api.md:103-107`
- `docs/sonarr-api.md:307-312`

The shared metadata model also needs explicit normalization rules for:

- Quality/source labels.
- MediaInfo dimensions versus quality resolution.
- Codec and dynamic-range values.
- Missing technical fields.
- Sonarr/Radarr custom-format differences.

### Stale Artwork Policy

The documents allow either stopping publication or retaining current artwork after stale metadata expires, but do not specify whether an expired badge should:

- Remain visible.
- Be removed by restoring the original.
- Be replaced with an unbadged copy.
- Be marked unavailable while retaining the current image.

References:

- `docs/data-model.md:694-706`
- `docs/architecture.md:331-346`
- `PLANS.md:315-358`

This is important because “leave current artwork unchanged” can otherwise leave stale badges indefinitely.

### Webhooks and Reverse Resolution

Webhook authentication, replay protection, secret rotation, source validation, and provider-record-to-Jellyfin resolution remain unspecified.

References:

- `docs/architecture.md:347-351`
- `docs/sonarr-api.md:335-340`
- `docs/radarr-api.md:587-599`
- `docs/media-metadata-mapping.md:12-15`

Webhooks should remain hints, but the endpoint security and resolution path must be defined before webhook work.

### Operational Defaults

Concrete values are still absent for:

- Queue size.
- Provider concurrency.
- Render concurrency.
- Retry/backoff.
- Response-size limits.
- Provenance retention.
- Artwork storage limits.
- Reconciliation cadence.
- Stale windows.

References:

- `docs/architecture.md:353-368`
- `PLANS.md:307-361`

The persisted architecture also adds storage for derived artwork and source preservation, so disk usage needs an explicit bound.

## IMPLEMENTATION-TIME

- Add per-item generation tokens, publication serialization, or equivalent compare-and-swap behavior.
- Mark ArrTags-generated item updates so they do not create reconciliation loops.
- Define safe provenance file permissions, path handling, cleanup, and bounded retention.
- Implement provider-specific DTO mapping and cross-provider normalization tests.
- Validate exact `SaveImage` storage behavior on the selected Jellyfin host configuration.
- Implement source capture, manual-image detection, restoration, and removal transitions.
- Split the broad milestones into small tasks at the service boundaries described by `implementation-planner.md`.
- Build contract fixtures for Sonarr/Radarr versions and malformed optional fields.
- Implement bounded provider inventories and batch reconciliation.
- Add integration tests for standard Jellyfin image routes after publication.

- Additional metadata providers.

- Non-poster artwork.
- Series/season aggregate badges.
- Expanded provider-version support.
- Advanced anime and alternate-version aggregation.
- Deeper Enhanced integration beyond independent coexistence.
- Additional visual primitives and extended technical metadata.

## Minimum Required Changes

Before V1 feature implementation:

1. Define `PublishedArtworkState` ownership evidence, source retention, manual-change detection, and restoration states.
2. Define crash recovery for the `SaveImage` plus provenance publication sequence.
3. Extend the canonical match model for Sonarr series, episode, and episode-file identity.
4. Decide V1 item/image scope and conservative behavior for unresolved file/numbering cases.
5. Define connection routing and ambiguity behavior for multiple Arr instances.
6. Define stale-artwork behavior after metadata freshness expires.
7. Remove or demote the duplicate architecture section and reconcile the research/planner wording.

Foundation work that does not publish artwork could proceed separately, but the V1 implementation sequence should stop at these decision boundaries.
