# ADR-022: Successive-Run Reconciliation Coverage

**Status:** Accepted (v1.2). This extends ADR-004's bounded-queue behavior with a
coverage guarantee and amends the reconciliation-coverage clause of
`docs/architecture/08-reconciliation-and-update-flow.md`.

**Date:** 2026-09-25

### Context

The scheduled and post-scan reconciliation enumerates the eligible movie and
episode candidates from the start of a deterministic order and enqueues the same
bounded `LibraryWorkHint` work as every other trigger
(`LibraryReconciliationService`). The bounded work queue accepts at most
`OperationalLimits.QueueCapacity` pending items and drops overflow rather than
blocking (`LibraryWorkQueue`), and the queue key is coalescing. Because every
run re-enumerates from index zero, a scope larger than `QueueCapacity` is
covered only by its prefix; successive runs overlap on that prefix instead of
advancing. This is limitation F4 in `docs/limitations/open.md` and is documented
as open in architecture section 8.

Two boundaries make the naive fix unsound, and this decision has to resolve both
rather than assume them away:

- `IWorkHintSink.TryEnqueue` returns a single boolean that is `false` for three
  different outcomes: the key is already in flight, the key is already pending
  (coalesce), and the pending count is at capacity (overflow). A caller that
  counts `true` results under-counts coalesced items and re-covers the same
  prefix; a caller that stops at the first `false` stalls on a coalesced
  duplicate. The service cannot locate the covered prefix from the boolean.
- `IMediaLibraryEnumerator.EnumerateCandidates(int startIndex, int maxItems)` is
  an integer offset into a Jellyfin query ordered only by `SortName` ascending.
  `SortName` is not unique and the library mutates between runs, so an integer
  offset can silently skip or re-cover items whenever the library changes before
  the cursor.

Event, webhook, and per-item triggers are not affected: they target a specific
item and are not bounded by the whole-scope prefix.

### Decision

ArrTags adds a **persisted, bounded reconciliation cursor** so successive runs
advance through the deterministic candidate order and eventually cover the whole
scope, without unbounded work in any one run.

1. **Enqueue outcome vocabulary.** The bounded enqueue boundary reports one of a
   fixed set of outcomes instead of a single boolean: `Accepted` (newly queued),
   `Coalesced` (the exact key is already pending), `InFlight` (the exact key is
   already being processed), `Overflow` (the pending count is at capacity and the
   work was dropped), and `Stopped` (the queue is not accepting work because the
   lifecycle fence is raised or the plugin is shutting down). `IWorkHintSink`
   gains a result-returning enqueue call carrying this bounded, non-secret
   outcome; the existing boolean `TryEnqueue` remains for the callers that only
   need enqueued-or-not (library events, webhooks, and the post-save trigger).
   The outcome is a bounded enum and is safe to log under the ADR-020 clause 4
   redaction contract.
2. **Cursor advance rule.** A whole-scope run enumerates the candidate order from
   the durable cursor. For each item the run either enqueues a hint or records
   that the item needs no work because it is ineligible or yields no hint; both
   are **covered**. The run tracks the position immediately after the last
   covered item and persists it as the new cursor when the run ends:
   - `Accepted`, `Coalesced`, and `InFlight` are all covered. A coalesced or
     in-flight item is already pending or processing, so the run continues
     without re-enqueuing it and does not stall.
   - `Overflow` stops the run at that item; the cursor is advanced only over the
     covered prefix and the next run resumes at the first uncovered (overflowed)
     item.
   - `Stopped` stops the run the same way.
   - An item that is inspected and correctly needs no work (ineligible,
     malformed, or otherwise no eligible hint) is covered and does not stop the
     run, so an ineligible item cannot stall the cursor.
   - At the end of the scope the cursor wraps to the start, so coverage is
     round-robin rather than a one-shot prefix. A cancellation advances the
     cursor only over the items already covered by that run.
3. **Stable cursor identity.** The cursor is an opaque `(SortName, itemId)` seek
   key, not an integer offset. The enumerator orders candidates by `SortName`
   ascending with the item id ascending as a unique tie-break (a total order) and
   gains a resume capability that returns the page strictly after a supplied key;
   `IMediaLibraryEnumerator` gains that capability. Task 19.1 implements the seek
   (a query predicate where the host query supports one, or a bounded linear skip
   at run start). Because the cursor is a key rather than an offset, an item
   added or removed before the cursor does not shift the resume point: an item
   added after the cursor is covered in the current cycle, and an item added
   before it is covered at the next wrap (or sooner after a scope reset). Adding
   or removing a library item therefore does **not** reset the cursor; only a
   scope change (clause 5) resets it. Coverage is guaranteed for a stable library
   and is best-effort for items added or removed mid-cycle; no stable item is
   skipped across a full cycle.
4. **Storage.** The cursor is a single bounded, versioned, integrity-checked
   plugin-state record (the existing `StateRepository` envelope shape). Its
   `StateAuthority` is `Cache`: the cursor is rebuildable, so an invalid or torn
   record is discarded by the repository and observed as a miss (it resets to the
   start) rather than quarantined. The record kind is the fixed constant
   `reconciliation-cursor` and the record id is fixed. The record carries only
   the scope identity (clause 5) and the opaque `(SortName, itemId)` position; it
   never carries an item path, provider payload, or credential. The bounded scope
   identity is the tuple of the sorted enabled-library id set and the supported
   item-type scope.
5. **Reset.** The cursor resets to the start when the reconciliation scope
   changes: when the recorded tuple of the enabled-library id set or the
   supported item-type scope differs from the current scope, so a removed or
   added library cannot leave the cursor pointing past unenumerated items. A
   missing, torn, or out-of-range cursor resets to the start rather than failing
   the run.
6. **Triggers.** The cursor governs only the whole-scope triggers: scheduled
   (periodic or manual) and post-scan. Jellyfin
   `ItemAdded`/`ItemUpdated`/`ItemRemoved` events, authenticated webhooks, and the
   bounded post-save trigger are unaffected and do not read or write the cursor.
   The post-save trigger is deliberately excluded even though it runs the same
   `LibraryReconciliationService` enumeration: it is a bounded, user-triggered
   prefix re-cover under the just-activated configuration, not the
   scheduled/post-scan whole-scope guarantee, so it always enumerates from the
   start and leaves the cursor untouched.
7. **Bounds.** One run still performs bounded work: it enumerates at most the
   batch size per page, checks cancellation between and inside pages, yields
   between pages, and stops as soon as the durable lifecycle fence refuses new
   work or the enqueue boundary reports `Overflow` or `Stopped`. The coverage
   guarantee is across successive runs, not a single run.

### Consequences

- A scope larger than `QueueCapacity` is fully covered across successive runs
  instead of the same prefix being re-covered.
- A coalesced or in-flight duplicate no longer stalls the cursor, and an overflow
  no longer causes the same prefix to be re-covered.
- A new bounded persisted record (`Cache` authority) is added to plugin state;
  the write is bounded and does not block a library-event handler.
- Operators may observe that a very large library takes several reconciliation
  intervals to cover completely; this is the intended bounded behavior.
- An item added before the cursor mid-cycle is covered at the next wrap rather
  than immediately; coverage is best-effort under concurrent mutation and
  guaranteed across a full cycle for a stable library.
- No provider call, render, or image write is added.

### Rejected alternatives

- **Stale/unknown-only enqueue.** Rejected: an item that never matches stays
  unknown and is re-enqueued every run, so it can starve the tail; it also
  requires a staleness scan over the whole scope before the queue bound applies.
- **Direct pipeline drive.** Rejected: it would run the whole scope outside the
  bounded queue in one long-lived operation, duplicating the reconciliation
  pipeline and weakening cancellation and lifecycle fencing.
- **Advance the cursor by the count of boolean `TryEnqueue` successes.** Rejected:
  the boolean conflates coalesce, in-flight, and overflow, so the covered prefix
  cannot be located (it under-counts covered items and repeats the prefix, or
  stalls on a coalesced duplicate).
- **Keep the integer-offset cursor.** Rejected: `SortName` is not unique and the
  library mutates between runs, so an offset silently skips or re-covers items.
