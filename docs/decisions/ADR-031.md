# ADR-031: Bounded Artwork Outcome Observability

**Status:** Accepted (v1.3). This amends ADR-025 clause 3 (the diagnostics counter
set) and is compatible with ADR-020 clause 4 as amended by ADR-026 (the
redaction contract and the bounded log subject). It does not change what ArrTags
selects, renders, or publishes.

**Date:** 2026-10-01

### Context

Two bounded, non-secret reasons are computed at the artwork boundary and then
discarded.

1. `ArtworkRegenerationPlanner.Decide` returns a bounded skip reason at six
   distinct sites (`src/ArrTags/Artwork/ArtworkRegenerationPlanner.cs:69`, `:74`,
   `:80`, `:90`, `:110`, `:128`) and a generate reason at `:132`. None of them
   reaches the log or any counter. Because a `Skip` performs no generation
   attempt, it also produces no `ArtworkGenerationCompleted` record — the artwork
   log line is emitted only from `ArtworkGenerationCoordinator.LogOutcome`, which
   runs after an attempt. A skipped subject is therefore completely silent.
2. `ArtworkPublisher.WriteRestoreBlocked` (`src/ArrTags/Artwork/ArtworkPublisher.cs:900-912`)
   writes the terminal `RestoreBlocked` state without emitting the bounded reason
   that caused it.

`DiagnosticsMetrics` counts render **failures** only:
`CreateRenderFailureCounts` (`src/ArrTags/Diagnostics/DiagnosticsMetrics.cs:168-189`)
increments one slot per `RenderFailureReason`, and only
`ArtworkGenerationCoordinator:140-143` records, and only for
`ArtworkGenerationOutcome.RenderFailed`. Pass-throughs, planner skips, and blocked
states are not represented anywhere in the ADR-025 snapshot.

ADR-008 (F8, v1.2) closed a narrower version of this gap: it made the bounded
render classification appear on the artwork log line, so two different
*generation-attempt* outcomes became distinguishable. It did not cover a decision
to not attempt generation, and it did not add a counter.

The observed cost, on a live host with a Radarr-only connection and a per-selector
`Quality` allowlist restricted to `CAM`/`TELESYNC`/`TELECINE`: three independent
subject classes produced no log line and no counter movement —

- one `OwnershipLost` (a host refresh re-adopted the sidecar; `V12-F7-1`),
- one `RestoreBlocked` (ADR-030's subject),
- roughly 645 subjects whose resolved badge selection was empty because the
  configured allowlist suppressed every value.

The first two are indistinguishable from a correct no-op. The third is
indistinguishable from a provider read failure, so an operator cannot tell a
deliberate configuration suppression from a broken pipeline without reading
`cache/metadata-state/*.json` and hand-correlating it. Diagnosing a single
affected subject took four diagnostic round trips against the filesystem, and two
intermediate hypotheses in that investigation were wrong.

### Decision

1. **Emit the decision, not just the attempt.** Every bounded
   `ArtworkRegenerationPlanner` decision — skip and generate alike — is emitted at
   `Information` on the existing artwork-boundary log line, carrying the bounded
   reason. The bounded restore-block reason is emitted the same way from the
   publisher. The ADR-026 bounded log subject applies unchanged: the primary
   media file name when a path is available, the Jellyfin item identifier
   otherwise.
2. **Extend the ADR-025 counter set.** `DiagnosticsSnapshot` gains bounded,
   process-lifetime artwork-outcome counters:
   - regeneration skipped, keyed by a code-owned bounded skip-reason enum;
   - ownership blocked, keyed by a code-owned bounded state enum;
   - restore blocked, keyed by a code-owned bounded reason enum.
   Each is a fixed set of slots sized from its enum, as
   `DiagnosticsMetrics` already does for render failures. Counters are
   process-lifetime, reset on restart, and never persisted.
3. **Counts and classifications only.** A counter key is a bounded enum value. No
   badge value, quality label, selector text, template, file name, item name,
   item identifier, path, provider payload, or credential is placed in a counter
   key, a counter label, or the snapshot. The number of selections suppressed by a
   selector allowlist is exposed as a **count**, never as the suppressed values.
   This keeps the snapshot inside the ADR-020 clause 4 redaction contract as
   amended by ADR-026.
4. **Shape stays fixed and bounded.** The snapshot remains fixed-shape with no
   per-item array and no unbounded collection. Adding these counters is a change
   to the ADR-025 clause 3 contract and is recorded here as that amendment; the
   elevation gate, the read-only route, and the absence of any write action are
   unchanged.
5. **Volume stays bounded.** Emission is subject to the existing
   `ArrTagsLog.LogThrottle`, which admits at most five records per category and
   event per minute and emits a suppression summary. A new bounded
   `ArrTagsLogEvent` member carries the decision record; the event set remains
   finite, so the ADR-020 clause 6 volume bound cannot be driven by
   caller-supplied keys.
6. **Panel.** The read-only settings-page diagnostics panel renders the new
   counters with the same fail-closed behavior: a missing or non-numeric count
   shows `0`, and an unrecognized health or state value shows its bounded
   fallback. The panel adds no setting and changes no saved value.
7. **Security review.** The extended endpoint and panel are security-reviewed
   before the phase gate, confirming the endpoint remains secret-free,
   administrator-gated, read-only, and fixed-shape.

### Consequences

- A subject with no badge now has a stated, machine-readable reason available in
  the host log at `Information` and as a process-lifetime count in the
  diagnostics panel, without reading state files.
- A deliberately allowlist-suppressed item is distinguishable from a provider
  read failure and from a skipped regeneration.
- A blocked ownership state is visible without hand-editing or hand-correlating
  the authoritative state tree.
- Log volume at `Information` and above increases for skipped subjects. The
  throttle bounds it, and the count in the snapshot is the reliable aggregate; the
  log is for per-subject correlation, not for counting.
- The snapshot shape grows by a fixed, bounded number of slots. Any consumer
  pinned to the exact prior shape must tolerate the extension; the panel is
  updated in the same phase.
- No selection, render, publication, fingerprint, or configuration behavior
  changes. This ADR makes an existing decision observable; it does not alter it.

### Rejected alternatives

- **Log the reason only, with no counter.** Rejected: the throttle caps
  per-subject lines at five per minute, so a whole-library run still cannot answer
  "how many items are in this state", which is the question an operator actually
  has. This is the same throttle limitation that made the origin investigation
  inconclusive from logs alone.
- **A per-item diagnostic endpoint listing affected subjects.** Rejected: it would
  put item identities, names, or paths behind an endpoint whose entire design
  guarantee is that it carries none of them, and it would need an unbounded
  collection.
- **Emit the suppressed badge value in the log or the counter.** Rejected: a
  quality label is provider-supplied text and would widen the redaction contract
  for no diagnostic gain; a count answers the same question.
- **Add the counters without logging the decision.** Rejected: counts cannot
  identify which subject is affected, and the origin session's core difficulty
  was per-subject correlation.
- **Reuse `RenderFailureCounts` for these outcomes.** Rejected: a skip and a
  failure are different classes, and a planner `Skip` never reaches the renderer,
  so folding them into the render-failure set would misreport a decision as a
  render fault.
