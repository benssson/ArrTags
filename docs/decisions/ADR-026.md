# ADR-026: Human-Readable Log Subject Identifier

**Status:** Accepted (v1.2). This amends ADR-020 clause 4's redaction contract by
adding a bounded, non-secret log subject to the allowed redacted-value set and by
adding an explicit directory/full-path exclusion.

**Date:** 2026-09-25

### Context

ADR-020 established bounded, redacted logging. Its clause 4 lists the values that
must never be emitted (an API key, the webhook secret, a `SecretLease` value, a
secret header, a raw request/response body, a full provider payload, or the
mutable `PluginConfiguration`) and allows only already-proven-bounded, redacted
values (`ArrProviderError` fields, safe secret reference, connection identity,
configuration version, bounded reason codes and enums, and item/record
identifiers). Clause 4 does not name a file-name subject and does **not** forbid
one either; it simply does not list a file name as an allowed value, and it has
no explicit directory/full-path exclusion because no path was ever allowed.

Several ArrTags boundaries emit the Jellyfin item identifier as the log subject:
the artwork-generation coordinator, the metadata reconciliation processor's
metadata-read-failure line and its discard line, the Sonarr/Radarr metadata
readers (resolved match), the work worker (processed and retry-scheduled, via
`WorkItemKey`), and the lifecycle service (item removed). The identifier is
stable but opaque; an operator cannot correlate a log line to a media file
without a second lookup.

Some of those call sites have the canonical `MediaIdentity`, whose
`MediaLocation.PrimaryPath` holds the raw path of the primary media source when
one exists (the coordinator's `MediaIdentity`, the metadata readers, and the
metadata reconciliation processor after identity creation). The work worker and
the lifecycle removal event do not have an identity and carry only the item
identifier; the metadata reconciliation processor's discard helper is called both
where an identity exists and where it does not.

The user-accepted decision is to replace the item identifier in log output with
the file name only (bounded), falling back to the item identifier when no path is
available.

### Decision

1. Log call sites that currently emit the Jellyfin item identifier emit a
   **bounded log subject** instead:
   - when the primary media path is available, the file name component only
     (`Path.GetFileName`), never a directory, drive, share, or parent path;
   - otherwise the existing Jellyfin item identifier in `D` format.
2. The file name is bounded to a documented maximum length (at most 128 Unicode
   scalar values), has control characters removed, and is otherwise emitted
   verbatim. A file name that is empty, whitespace, or reduces to nothing after
   normalization falls back to the item identifier.
3. The bounded log subject is threaded through every item-id-emitting site, with
   an explicit fallback where no path is available:
   - **Identity-bearing sites (path available when present):**
     `ArtworkGenerationCoordinator` (the generation log; `request.MediaIdentity`),
     the `MetadataReconciliationProcessor` metadata-read-failure line (after
     `MediaIdentityFactory.TryCreate`), and the Sonarr/Radarr `*MetadataReader`
     resolved-match log (identity available).
   - **Mixed site:** `MetadataReconciliationProcessor.Discard(itemId, reason)`
     takes only the item id and is called both where an identity exists
     (changed-basis discards after identity creation) and where it does not
     (version mismatch before item resolve, item missing, identity creation
     failed, ineligible, or connection unavailable). The discard log-subject
     helper must use the file name when a path is available and fall back to the
     item id otherwise; it must not thread a path where none exists.
   - **Fallback sites (item id only):** `LibraryWorkWorker` (via `WorkItemKey`)
     and the `ArrTagsLifecycleService` item-removed event.
   - **No item identifier is emitted (no change):**
     `ConcurrencyLimitedArrMetadataReader`, `WebhookIntakeService`,
     `WebhookAuthenticationFilter`, and `LibraryReconciliationService` emit only
     connection identity, counts, or fixed reasons.
4. The ADR-020 clause 4 secret-exclusion set is unchanged: no API key, webhook
   secret, `SecretLease` value, `X-Api-Key`/`X-ArrTags-Webhook-Secret` header, raw
   request/response body, full provider payload, or mutable `PluginConfiguration`
   is logged. This ADR **adds** the bounded log subject to the allowed
   redacted-value set and **adds** an explicit exclusion for a directory, drive,
   share, or full path (previously not named because no path was allowed). All
   other clause 4 values and exclusions remain in force.
5. Because a media file name may itself be sensitive, this is a security-relevant
   amendment and requires a fresh security review of the log path and its
   redaction tests.

### Consequences

- Operators can correlate an artwork or matching log line with a media file
  without a separate item lookup.
- A media file name (which may reveal a title) can appear in the host log; this
  is the accepted trade-off and is bounded, normalized, and fallback-safe.
- Full paths, directories, and all secret-bearing values remain excluded; the
  directory/full-path exclusion is now explicit in the clause 4 contract.
- The bounded log subject is added to the allowed redacted-value set; the
  redaction tests are extended at every verbosity level.

### Rejected alternatives

- **Keep the item identifier only.** Rejected: it is the usability gap the
  decision removes.
- **Log the full path.** Rejected: directory structure and share names are more
  sensitive than the bounded file name and are not needed for correlation.
- **Hash the identifier or path.** Rejected: a hash is not human-readable and is
  not the accepted decision.
