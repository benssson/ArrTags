# ADR-026: Human-Readable Log Subject Identifier

**Status:** Accepted (v1.2). This amends ADR-020 clause 4's redaction contract by
adding a bounded, non-secret log subject to the allowed redacted-value set and by
adding an explicit directory/full-path exclusion.

**Date:** 2026-09-25

### Context

ADR-020 established bounded, redacted logging. Its clause 4 lists the values that
must never be emitted (an API key, the webhook secret, a `SecretLease` value, a
secret header, a raw request/response body, a full provider payload, or the
mutable `PluginConfiguration`) and allows only already-proven-bounded, redacted
values (`ArrProviderError` fields, safe secret reference, connection identity,
configuration version, bounded reason codes and enums, and item/record
identifiers). Clause 4 does not name a file-name subject and does **not** forbid
one either; it simply does not list a file name as an allowed value, and it has
no explicit directory/full-path exclusion because no path was ever allowed.

Several ArrTags boundaries emit the Jellyfin item identifier as the log subject:
the artwork-generation coordinator, the metadata reconciliation processor's
metadata-read-failure line and its discard line, the Sonarr/Radarr metadata
readers (resolved match), the work worker (processed and retry-scheduled, via
`WorkItemKey`), and the lifecycle service (item removed). The identifier is
stable but opaque; an operator cannot correlate a log line to a media file
without a second lookup.

Some of those call sites have the canonical `MediaIdentity`, whose
`MediaLocation.PrimaryPath` holds the raw path of the primary media source when
one exists (the coordinator's `MediaIdentity`, the metadata readers, and the
metadata reconciliation processor after identity creation). The work worker and
the lifecycle removal event do not have an identity and carry only the item
identifier; the metadata reconciliation processor's discard helper is called both
where an identity exists and where it does not.

The user-accepted decision is to replace the item identifier in log output with
the file name only (bounded), falling back to the item identifier when no path is
available.

### Decision

1. Log call sites that currently emit the Jellyfin item identifier emit a
   **bounded log subject** instead:
   - when the primary media path is available, the file name component only
     (`Path.GetFileName`), never a directory, drive, share, or parent path;
   - otherwise the existing Jellyfin item identifier in `D` format.
2. The file name is bounded to a documented maximum length (at most 128 Unicode
   scalar values), has control characters removed, and is otherwise emitted
   verbatim. A file name that is empty, whitespace, or reduces to nothing after
   normalization falls back to the item identifier.
3. The bounded log subject is threaded through every item-id-emitting site, with
   an explicit fallback where no path is available:
   - **Identity-bearing sites (path available when present):**
     `ArtworkGenerationCoordinator` (the generation log; `request.MediaIdentity`),
     the `MetadataReconciliationProcessor` metadata-read-failure line (after
     `MediaIdentityFactory.TryCreate`), and the Sonarr/Radarr `*MetadataReader`
     resolved-match log (identity available).
   - **Mixed site:** `MetadataReconciliationProcessor.Discard(itemId, reason)`
     takes only the item id and is called both where an identity exists
     (changed-basis discards after identity creation) and where it does not
     (version mismatch before item resolve, item missing, identity creation
     failed, ineligible, or connection unavailable). The discard log-subject
     helper must use the file name when a path is available and fall back to the
     item id otherwise; it must not thread a path where none exists.
   - **Fallback sites (item id only):** `LibraryWorkWorker` (via `WorkItemKey`)
     and the `ArrTagsLifecycleService` item-removed event.
   - **No item identifier is emitted (no change):**
     `ConcurrencyLimitedArrMetadataReader`, `WebhookIntakeService`,
     `WebhookAuthenticationFilter`, and `LibraryReconciliationService` emit only
     connection identity, counts, or fixed reasons.
4. The ADR-020 clause 4 secret-exclusion set is unchanged: no API key, webhook
   secret, `SecretLease` value, `X-Api-Key`/`X-ArrTags-Webhook-Secret` header, raw
   request/response body, full provider payload, or mutable `PluginConfiguration`
   is logged. This ADR **adds** the bounded log subject to the allowed
   redacted-value set and **adds** an explicit exclusion for a directory, drive,
   share, or full path (previously not named because no path was allowed). All
   other clause 4 values and exclusions remain in force.
5. Because a media file name may itself be sensitive, this is a security-relevant
   amendment and requires a fresh security review of the log path and its
   redaction tests.

### Consequences

- Operators can correlate an artwork or matching log line with a media file
  without a separate item lookup.
- A media file name (which may reveal a title) can appear in the host log; this
  is the accepted trade-off and is bounded, normalized, and fallback-safe.
- Full paths, directories, and all secret-bearing values remain excluded; the
  directory/full-path exclusion is now explicit in the clause 4 contract.
- The bounded log subject is added to the allowed redacted-value set; the
  redaction tests are extended at every verbosity level.

### Implementation note (v1.2, tasks 15.1-15.4)

The decision shipped as specified; no clause above is rewritten.

- Task 15.1 added the shared helper `src/ArrTags/Logging/LogSubject.cs`: the
  file-name component only (`Path.GetFileName`), the documented
  `MaximumScalarValues = 128` Unicode-scalar bound applied after control-scalar
  removal in one scalar-wise pass (a surrogate pair is never split), otherwise
  verbatim emission, and the `D`-format item-identifier fallback for a null,
  empty, whitespace, control-only, or control-reduced-to-whitespace name.
  `LogSubjectTests` (23 cases) covers the policy.
- Task 15.2 threaded the helper through every clause 3 site: the artwork
  coordinator, both `MetadataReconciliationProcessor` metadata-read-failure
  paths (the reader-threw catch and the failed-read result), the Sonarr/Radarr
  `LogMatch` records, the mixed discard overload (path when given, otherwise
  the item id), and the explicit item-id fallback sites (`LibraryWorkWorker`
  processed and retry-scheduled records, which retain the bounded
  connection/surface context, and the `ArrTagsLifecycleService` item-removed
  event). `LogRedactionTests` covers each site at every verbosity level.
- Task 15.3 emitted the specific bounded render classification on the
  artwork-boundary outcome line (` (PassThroughReason=<value>)`,
  ` (FailureReason=<value>)`, or ` (SourceFailureReason=<value>)` when the
  result carries one), which resolves limitation F8.
- Task 15.4 added ADR-020's amendment note, reconciled the canonical
  documentation, and recorded the clause 5 security review at
  `docs/implementation/15.4/security-review.json`.

Clause 3's mixed-site parenthetical classes the ineligible and
connection-unavailable pre-publish discards as sites where no identity exists;
in the code those discards run after identity creation, where a path is
available. The implementation follows the clause 3 enumeration and threads no
path at those sites, so they take the item-id fallback; this note records the
wording discrepancy rather than rewriting the clause. The clause 1 exclusion is
a host-native-path statement: `Path.GetFileName` uses host-platform separator
semantics, and the POSIX behavior (a Windows-style backslash string is a single
file name, not a path) is what the pinned Linux host and the tests exercise.

Control removal is Cc-only: `Rune.IsControl` matches the Unicode Control
category, which is the literal reading of clause 2's "control characters
removed". Unicode Cf format characters (for example U+202E RIGHT-TO-LEFT
OVERRIDE and U+200B ZERO WIDTH SPACE) and the Zl/Zp separators U+2028/U+2029
therefore pass through verbatim. The task 15.4 security review adjudicated this
as **not** a clause 2 violation and a non-secret log-integrity observation, not
a secret exposure (SR-15.4-01, LOW, open as optional hardening; bounded at 128
scalars and not part of the volume-bound throttle key) in
`docs/implementation/15.4/security-review.json`.

### Implementation note (v1.2, task 21.11: SEC-21.5-02 and SEC-21.5-03)

The Decision clauses above are unchanged. This note records the hardening the
task 21.10 security review's two carried LOW findings required. It **supersedes
two reading-level statements in the task 15.1-15.4 implementation note above**:
that note described the then-shipped code rather than the decision, so its
"Cc-only" control-removal reading and its "host-native-path" separator-scope
reading no longer describe the shipped code and are not rewritten (history is
immutable; the accepted clauses already require a bounded, otherwise-verbatim
subject and clause 1's directory/full-path exclusion, so this is an
implementation correction, not an amendment).

- **Removal predicate (SEC-21.5-02).** `LogSubject.NormalizeFileName` removes
  exactly the four non-printing categories Unicode `Cc` (Control), `Cf`
  (Format, including U+200B/U+200D, U+202A-U+202E, U+2066-U+2069, U+00AD, and
  the bidi controls), `Zl` (Line Separator, U+2028), and `Zp` (Paragraph
  Separator, U+2029), in the existing single scalar-wise pass. Every other
  category is preserved, including `Mn` (combining marks), `Zs` (space
  separators), `Co` (private use), `Cn` (unassigned), letters, and emoji. The
  predicate is a superset of the pre-fix `Rune.IsControl` (Cc-only) predicate,
  so an ordinary control is still removed.
- **Final-component extraction (SEC-21.5-03).** The final component is the
  substring after the last '/' and after the last '\', whichever is later, on
  every host, so the exclusion is no longer host-platform-scoped: a
  Windows-style, UNC, or mixed-separator primary path yields the file name
  only, and a POSIX file name that itself contains a backslash is truncated to
  the text after that backslash (a strictly shorter, safer subject).
- **Preserved properties.** The `MaximumScalarValues = 128` bound is applied
  after removal, the single pass still never splits a surrogate pair, and
  whitespace is still neither collapsed nor trimmed. The empty/whitespace check
  is re-run on the extracted component, the post-normalization fallback check
  still runs, and a path that is empty, whitespace, or only separators, or
  whose component reduces to nothing after removal, still falls back to the
  item identifier in `D` format. `LogSubjectTests` covers the widened predicate
  (with ordinary-Cc, non-ASCII, decomposed-combining, and astral-plane positive
  controls), the Windows/UNC/mixed-separator component cases, the unchanged
  URL-shaped SR-15.4-04 observation, and the preserved bounds; the new cases
  fail on the pre-fix code. The release security review of the corrected
  candidate (task 21.14) owns the disposition of both findings.

### Rejected alternatives

- **Keep the item identifier only.** Rejected: it is the usability gap the
  decision removes.
- **Log the full path.** Rejected: directory structure and share names are more
  sensitive than the bounded file name and are not needed for correlation.
- **Hash the identifier or path.** Rejected: a hash is not human-readable and is
  not the accepted decision.
