# ADR-028: Limit Display Units and Restart-Required Settings Surfacing

**Status:** Accepted (v1.2). This amends ADR-016's dashboard settings-page
contract by adding presentation units and restart-required surfacing; it does not
change the save path or the elevation boundary.

**Date:** 2026-09-25

### Context

Byte-denominated operational limits (`ProviderResponseLimitBytes`,
`WebhookMaxPayloadBytes`, `SourceArtifactLimitBytes`, `DerivedArtifactLimitBytes`,
`RenderCacheQuotaBytes`, `ArtifactStorageQuotaBytes`, `InventoryCacheMaxBytes`)
are persisted as bytes and shown in the settings page as raw byte counts with
byte validation ranges. Raw byte counts are hard to read and error-prone.

Their validation ranges and defaults are (from `OperationalLimits.Validate` and
the properties):

| Field | Minimum | Default | Maximum |
| --- | --- | --- | --- |
| `ProviderResponseLimitBytes` | 64 KiB | 8 MiB | 64 MiB |
| `WebhookMaxPayloadBytes` | 4 KiB | 256 KiB | 4 MiB |
| `SourceArtifactLimitBytes` | 64 KiB | 32 MiB | 128 MiB |
| `DerivedArtifactLimitBytes` | 64 KiB | 32 MiB | 128 MiB |
| `RenderCacheQuotaBytes` | 64 MiB | 1 GiB | 64 GiB |
| `ArtifactStorageQuotaBytes` | 256 MiB | 4 GiB | 256 GiB |
| `InventoryCacheMaxBytes` | 1 MiB | 32 MiB | 256 MiB |

Three fields have a minimum below 1 MiB while their default and maximum are
MiB-scale, so a rule based on the current value would switch unit mid-range and
make the range label ambiguous. A plain integer MB input cannot represent their
64 KiB minimum exactly.

Separately, some settings take effect at runtime through the ADR-016 snapshot
replacement, while others are captured by singletons at construction and change
only after a host restart (for example the `StateRepository`-backed render cache
TTL/quota and terminal-provenance retention, and the artifact-size/decode limits
captured by the artwork-store singletons, including
`ArtifactStorageQuotaBytes`). Some limits have **both** a construction-captured
consumer and a per-operation consumer. The examples above are illustrative; the
complete classification with per-consumer evidence is owned by task 16.2, not by
this ADR. The settings page currently gives no indication of which is which, and
a saved change to a restart-required setting silently appears to have no effect.

The user-accepted decisions are: expose byte-denominated limits in binary MB
(the webhook payload limit may remain in KB); keep the internal and persisted
representation in bytes with exact byte round-trip; and add restart-required
note text plus, where possible, a modal reminder when a restart-required setting
changes.

### Decision

1. **Units and precision.** Each byte-denominated field has a unit and a step
   fixed **per field in code**, not chosen per value:
   - Every byte limit is displayed in binary megabytes (`1 MB = 1,048,576 bytes`)
     except `WebhookMaxPayloadBytes`, which is displayed in binary kibibytes
     (`1 KB = 1,024 bytes`).
   - Each field declares a fixed step `S` in bytes that divides its minimum,
     default, and maximum: `S = 64 KiB` (1/16 MB) for
     `ProviderResponseLimitBytes`, `SourceArtifactLimitBytes`, and
     `DerivedArtifactLimitBytes`; `S = 1 MiB` for `RenderCacheQuotaBytes`,
     `ArtifactStorageQuotaBytes`, and `InventoryCacheMaxBytes`; and `S = 1 KiB`
     for `WebhookMaxPayloadBytes`.
   - Each field declares a fixed display precision `P`: 4 fractional digits for
     the 64-KiB-step MB fields (so 64 KiB displays as `0.0625 MB`), and 0
     fractional digits for the whole-MiB and whole-KiB fields; the rendered value
     trims trailing zeros.
   - The range label is shown in the field's fixed unit and precision, including
     when the range spans the 1 MiB boundary; the sub-1-MiB bound is shown as a
     fraction in the field's unit (for example `0.0625 – 64 MB`) and is never
     switched to a different unit. There is therefore no per-value unit switch
     and no ambiguous range unit.
   - **Conversion algorithm.** The settings input accepts at most `P` fractional
     digits and its `step` is `S / U` (for example `0.0625` for the 64-KiB-step
     MB fields and `1` for the whole-unit fields). Store from display: parse the
     decimal as a scaled integer (scaled by `10^P`) and compute
     `bytes = round(scaled * U / 10^P)`; a value that does not land on the step
     (for example `0.1 MB` for a 64-KiB-step field, which would compute
     104858 bytes) is rejected rather than silently rounded. This step-multiple
     rejection is a **new** check introduced by this change, owned by task 16.1:
     the existing `OperationalLimits.Validate` enforces only the field's byte
     range, not step alignment, so the settings conversion/validation path (and,
     where the page uses native constraint validation, the input's `step`
     attribute) must add an explicit step check. The internal
     `OperationalLimits` byte-range validation is unchanged. Display from store:
     `display = bytes / U` rendered at precision `P`.
   - Because every minimum, default, and maximum is an exact multiple of its
     field step, display → store → display and store → display → store preserve
     the exact byte value at the minimum, default, and maximum of every field
     (including the 64 KiB minima). The internal `OperationalLimits` values and
     the persisted XML remain in bytes; only the settings-page presentation and
     its validation-range labels change.
2. **Restart-required set.** The authoritative set of settings that require a
   host restart is code-owned and code-evidenced. The classification is binary:
   - a setting is **restart-required** when **any** consumer resolves the value at
     singleton construction;
   - a setting is **per-operation** only when every consumer resolves it from the
     current configuration snapshot on each operation.
   A setting with both kinds of consumer is classified restart-required, and its
   note text states that some paths apply the change immediately while others
   require a restart. The classification is recorded with per-consumer evidence
   and is testable. Task 16.2 is the single owner of the complete set (including
   `ArtifactStorageQuotaBytes` and the per-operation `ProviderResponseLimitBytes`,
   `WebhookMaxPayloadBytes`, and `InventoryCacheMaxBytes`, and the mixed limits
   `SourceArtifactLimitBytes`, `DerivedArtifactLimitBytes`, and
   `MaxImageDimensionPixels`), and it records the per-consumer evidence for the
   mixed limits.
3. **Note text.** The settings page marks every restart-required setting with
   note text stating that a server restart is required for the change to take
   effect. The note text is always present. For a mixed setting the note text
   also states that some paths apply the change immediately.
4. **Modal reminder.** When a restart-required setting changes on save, the page
   shows a modal reminder, where the jellyfin-web modal/notification API supports
   it. If the modal API is not available or not stable, the note text is the
   fail-open behavior and the remaining behavior is unchanged. The modal research
   is owned by a `jellyfin-expert` spike task before the modal is implemented, and
   the spike records the API's availability and stability.
5. This does not change the elevation-gated `PluginsController` save path, the
   last-valid retention behavior, or the set of restart-required settings during
   the course of this release; it only makes the classification visible.

### Consequences

- Operators read and edit byte limits in familiar units without losing byte
  precision; the 64 KiB minima display exactly as a fraction of MB.
- Operators can tell which changes apply immediately and which need a restart,
  reducing "the setting didn't work" reports for restart-required values; a mixed
  setting is marked restart-required and says so.
- The restart-required classification becomes a maintained contract whose
  complete membership is recorded by task 16.2; adding a future limit requires
  classifying it as per-operation or restart-required.
- The page gains a small amount of unit-conversion and rendering logic; no
  secret or new data endpoint is introduced.

### Implementation note (v1.2, tasks 16.1-16.6)

The decision shipped as specified; no clause above is rewritten.

- Task 16.1 added the code-owned display mapping
  (`src/ArrTags/Configuration/ByteLimitUnits.cs`, `ByteLimitField.cs`): the fixed
  binary unit (MB, except `WebhookMaxPayloadBytes` in KB), the fixed step
  (64 KiB for the three 64-KiB-step MB fields, 1 MiB for the whole-MiB fields,
  1 KiB for the webhook field), and the fixed precision (4 fractional digits for
  the 64-KiB-step fields, 0 otherwise), with the unchanged
  `OperationalLimits.Validate` byte bounds. Display uses the clause 1
  scaled-integer algorithm with trailing zeros trimmed, and store rejects a
  value that is not an exact step multiple rather than rounding it.
  `src/ArrTags/Configuration/config.html` mirrors the mapping, declares the
  native unit `min`/`max`/`step`, converts the displayed value back to bytes
  before the save request, and stores only the converted bytes. The persisted
  XML and the internal `OperationalLimits` values remain bytes. The page is a
  static embedded resource and the repository has no JavaScript runtime, so the
  page half is pinned by structural tests over the served resource against the
  code-owned mapping, and the conversion itself is exercised as real C# through
  `ByteLimitUnits`.
- Task 16.2 added the code-owned restart-required classification
  (`src/ArrTags/Configuration/RestartRequiredSettings.cs`) over every writable
  property of the five configuration model types the settings page round-trips:
  43 settings, seven restart-required
  (`SourceArtifactLimitBytes`, `DerivedArtifactLimitBytes`, and
  `MaxImageDimensionPixels` mixed; `RenderCacheTtlMinutes`,
  `RenderCacheQuotaBytes`, `ArtifactStorageQuotaBytes`, and
  `TerminalProvenanceRetentionDays` construction-only). The per-consumer audit
  is recorded at `docs/implementation/16.2/consumer-evidence.md`.
- Task 16.3 added the always-present static note text next to every
  restart-required settings-page element; a mixed setting's note also states
  that some paths apply the change immediately. Task 16.4 recorded the modal-API
  spike (`docs/research/jellyfin-expert/modal-notification-api.json`): the
  pinned jellyfin-web exposes `Dashboard.alert({ title, message })` as a public
  but potentially unstable compatibility shim (in-source TODO removal) and no
  server-versioned notification API. Task 16.5 implemented the best-effort
  reminder per the spike: it fires only when a classified value changed on an
  accepted save, after the preserved
  `Dashboard.processPluginConfigurationUpdateResult` call, behind a lazily
  resolved `window.Dashboard` presence/type guard and a swallowing
  `try`/`catch`, so an absent or failing modal API changes nothing and the note
  text remains the authoritative behavior. Escape/backdrop dismissal is
  accepted as the shim's benign unhandled rejection.
- Task 16.6 composed the G6/G8 flow without a live host in
  `tests/ArrTags.Tests/GoalG6G8IntegrationTests.cs`: the seven displayed values
  travel through the pinned dashboard POST JSON deserialization, the real
  `Plugin.UpdateConfiguration` validate/persist/activate path, and the real XML
  boundary, and every minimum, default, and maximum (including the three 64 KiB
  minima) round-trips exactly; the classification is composed with the page
  mirror, the static notes, and the reminder detection domain, including the
  restart-required byte limits that flow through both features. The modal and
  the page conversion remain structurally verified only (no JavaScript runtime;
  the pinned live matrix runs `--nowebclient`); the accepted residuals are
  registered as `V12-G6-1` (legacy off-step values) and `V12-G8-1`/`V12-G8-2`
  in `docs/limitations/00-index.md`.
- A persisted in-range off-step byte value (possible from the pre-16.1 page, for
  example 100000 for `ProviderResponseLimitBytes`) still loads unchanged and is
  displayed at the field's fixed precision; on the next save it is re-quantized
  to the nearest whole unit for the whole-KiB/whole-MiB fields or rejected until
  edited for the three 64-KiB-step MB fields. This is the clause 1
  reject-rather-than-round behavior outside the exact min/default/max
  round-trip guarantee, registered as `V12-G6-1`.

### Rejected alternatives

- **Display in decimal MB/MB-SI.** Rejected: the persisted and validated values
  are binary; a decimal display would introduce round-trip ambiguity.
- **Change the persisted representation to MB.** Rejected: it would break the
  existing XML and the exact byte semantics.
- **Choose the unit per current value.** Rejected: a range that spans 1 MiB would
  switch unit mid-range and make the range label ambiguous.
- **Display a sub-1-MiB minimum by switching the field to KB.** Rejected: it
  changes the field's unit mid-range and contradicts the per-field decision; the
  exact fraction in MB is used instead.
- **A generic "some settings need a restart" note.** Rejected: it does not tell
  the operator which setting needs one.
- **A modal as the only mechanism.** Rejected: it is not guaranteed available and
  the note text must be the reliable fallback.
