# ADR-027: Extra Large Badge Size

**Status:** Accepted (v1.2). This extends ADR-019 clause 3's size enum and factor
list.

**Date:** 2026-09-25

### Context

ADR-019 clause 3 defines configurable badge size as an enum with `Small`,
`Medium`, and `Large`, with code-owned factors `0.75`, `1.0`, and `1.5`, and an
effective scale clamped so the badge still fits the safe area. The settings
dropdown currently offers Medium, Small, Large. Operators want a larger preset.

`BadgeSize.Medium` is the numeric zero so an absent or zero-valued persisted
field reproduces the V1 geometry. The effective size participates in the
renderer-configuration and render fingerprints only when it is not the default;
a non-default size changes the fingerprint and republishes the affected item.
Adding a new enum member and factor does not change how any existing value
renders.

### Decision

ArrTags adds an Extra Large badge size.

1. `BadgeSize` gains `ExtraLarge` (numeric value 3). The code-owned factors are
   `Small = 0.75`, `Medium = 1.0`, `Large = 1.5`, `ExtraLarge = 2.0`, each
   relative to Medium.
2. The effective scale remains `clamp(width / 1000, 0.5, 4.0) * sizeFactor`,
   clamped so the badge still fits the safe area; an Extra Large badge that
   cannot fit falls back to the existing shorten/omit behavior rather than
   overflowing.
3. The settings dropdown order is **Small, Medium, Large, Extra Large**.
4. **Version decision.** Adding the enum member does not change any existing
   output: the default (`Medium`) is unchanged, and the renderer-configuration
   fingerprint and render output fingerprint already include any non-default
   size, so selecting Extra Large republishes only the items whose policy selects
   it. Therefore `RenderVersion.CurrentRendererVersion` and
   `RendererConfiguration.CurrentSchemaVersion` do **not** advance for this
   change. New golden coverage for Extra Large is required, and the existing
   committed goldens must remain byte-identical; if any existing golden changes,
   the version decision is reconsidered rather than silently advancing.
5. No per-selector size is added; size remains global renderer policy.
6. The implementation extends `BadgeGeometry.SizeFactor` with the new member (the
   current switch throws for an unknown value) and adds `RendererConfiguration`
   validation coverage for it; the existing `Enum.IsDefined` check accepts the new
   defined value. The task must extend both the geometry factor and the
   validation coverage.

### Consequences

- Operators can choose a larger preset, with the same safe-area, text, contrast,
  and determinism guarantees as the other sizes.
- Existing configurations and goldens are unaffected.
- An Extra Large selection is output-affecting for the items that select it and
  republishes their artwork through the normal fingerprint path.
- New layout goldens and safe-area tests are added.

### Implementation note (v1.2, tasks 18.1-18.3)

The decision shipped as specified; no clause above is rewritten.

- Task 18.1 added `BadgeSize.ExtraLarge = 3` and the code-owned
  `BadgeGeometry.ExtraLargeSizeFactor = 2.0` with the `SizeFactor` switch arm
  (clause 1). `ComputeEffectiveScale` and its safe-area clamp are unchanged:
  they already bound factor `2.0` and keep the existing shorten/omit fallback
  (clause 2). `RendererConfiguration.Validate` is unchanged because the existing
  `Enum.IsDefined` check already accepts the defined member, and the required
  validation coverage is added as tests (clause 6).
  `src/ArrTags/Configuration/config.html` orders the badge-size dropdown
  Small, Medium, Large, Extra Large with `value="ExtraLarge"` (clause 3).
- Task 18.2 added the two required goldens (`bottom-left-extra-large` and
  `full-rail-extra-large`, both at the default `BottomLeft` anchor) and verified
  the version decision (clause 4): the pinned native oracle reproduced every
  existing Small/Medium/Large golden byte-identically (pre-task Failed 0,
  Passed 15, Skipped 0, Total 15; post-task Failed 0, Passed 17, Skipped 0,
  Total 17), no existing golden or manifest entry changed, and neither
  `RenderVersion.CurrentRendererVersion` (3) nor
  `RendererConfiguration.CurrentSchemaVersion` (2) advanced. The new goldens
  rendered byte-identically across separate generator processes.
- Task 18.3 reconciled the canonical documentation (including this note and the
  ADR-019 extension note) and ran the G7 integration verification: the
  structural page test pins the dropdown order and the `ExtraLarge` option
  value; `RendererOutputPolicy.Size` resolves to
  `BadgeGeometry.SizeFactor(BadgeSize.ExtraLarge) == 2.0` through the
  `ComputeEffectiveScale` safe-area clamp; a non-default size changes the
  renderer-configuration and output fingerprints; the default suite is Failed 0,
  Passed 1799, Skipped 64, Total 1863 and the pinned native golden run is
  Failed 0, Passed 17, Skipped 0, Total 17.

Test sensitivity was probed by tasks 18.1-18.2, as recorded in their reports:
removing the switch arm failed 9 `BadgeSizePositionTests` cases; making
`RendererConfiguration.Validate` reject `ExtraLarge` failed the new validation
fact; skipping the renderer-configuration fingerprint entry failed the same
fact; swapping the `Large`/`Extra Large` options failed the dropdown-order fact;
disabling the safe-area clamp failed 5 clamp cases; and corrupting, mutating, or
removing a new golden failed the fixture case and the manifest-completeness fact
(2 failures each). Every probe was reverted.

### Rejected alternatives

- **Advance `RenderVersion` unconditionally.** Rejected: it would force every
  published poster to re-render for a change that alters no existing output.
- **A numeric size multiplier instead of a preset.** Rejected: presets match the
  existing ADR-019 decision and keep the settings UI simple.
- **An unbounded factor.** Rejected: the safe-area clamp and shorten/omit
  behavior bound the geometry; a larger preset must still fit the safe area.
