# ADR-023: Version-Aware Post-Save Re-Render

**Status:** Accepted (v1.2). This amends the coalescing clause of
`docs/architecture/08-reconciliation-and-update-flow.md` (the version-blind
coalescing contract) and depends on, but does not amend, ADR-004's bounded queue
and per-item single-flight behavior.

**Date:** 2026-09-25

### Context

A configuration save activates the new snapshot (`Plugin.UpdateConfiguration` ->
`ConfigurationSnapshotService.TryReplace`) and then requests the bounded
post-save reconciliation, which enqueues a work hint carrying the new
configuration version for each eligible item. The queue key is the item,
connection, and image surface and deliberately excludes the configuration
version (`WorkItemKey`), and the queue coalesces any hint whose key is already
pending or in flight (`LibraryWorkQueue`; architecture section 8's coalescing
clause). A new-version hint for an item that is already pending or in flight
under the previous version is therefore dropped, and the outstanding item then
discards itself at processing time as a stale basis and is completed without
re-enqueueing. The item keeps its previously published artwork until a later
trigger enqueues it with the current version. This is limitation F6 in
`docs/limitations/open.md`.

The coalescing identity is deliberately version-blind so that `WorkItemKey`
remains a bounded, secret-free, path-free record and so that single-flight per
item and image surface is preserved. Changing the key to be version-aware would
let two entries exist for the same item/surface and risks duplicated concurrent
work unless a second layer of per-surface single-flight is introduced.

Two implementation facts shape the decision:

- A re-enqueue issued from inside the processing/discard path is silently
  coalesced away, because the queue rejects a same-key enqueue while that key is
  in flight and the worker releases the in-flight slot only in its `finally`
  block after processing returns.
- Every discard currently returns the same successful, non-retryable
  `WorkProcessingResult.Completed(reason)` whose only distinction is free text, so
  the worker cannot identify a version-mismatch discard versus an item-missing,
  ineligible, or connection-changed discard.

### Decision

ArrTags closes the gap at the **stale-basis discard boundary** instead of
changing the coalescing identity.

1. **Machine-readable discard classification.** A discard carries a bounded
   `DiscardReason`: `ConfigurationStale`, `ItemMissing`, `Ineligible`,
   `ConnectionChanged`, or `IdentityUnavailable`. `ConfigurationStale` means the
   work item's carried configuration version is no longer the current
   configuration version at the discard point; it covers both the initial
   version check and the pre-publication version re-check. The other
   classifications describe the real reason the item could not be processed and
   are never treated as stale basis.
2. **Bounded re-enqueue.** Exactly one classification — `ConfigurationStale` —
   causes the worker to re-enqueue exactly one fresh `LibraryWorkItem` at the
   current configuration version for the same `WorkItemKey`. A discard with any
   other classification, a same-version discard, a stopped queue, and an
   overflowed queue do not re-enqueue.
3. **Ordering versus single-flight.** The re-enqueue happens **after** the
   in-flight slot is released: the worker records that the item discarded as a
   stale basis, calls `CompleteProcessing(item.Key)` to release the slot, and
   only then enqueues the fresh current-version item. If the queue is stopped or
   full the re-enqueue is dropped (bounded), never blocked. A coverage test must
   fail if the re-enqueue is issued before the slot is released.
4. **Bound.** The bound is implicit in the version carried by the re-enqueued
   item: the fresh item carries the current configuration version, so the
   version check can never again classify it as `ConfigurationStale`, and a
   same-version repeat is impossible. No separate per-key version set or other
   version storage is required; the effective bound is one re-enqueue per (item,
   connection, image surface, configuration version).
5. **Eligibility is determined after the version check.** The version check
   precedes the item resolve and eligibility checks. An item that is by then
   ineligible, absent, or identity-less is therefore re-enqueued once as a
   `ConfigurationStale` discard and then discarded on the next pass for its real
   reason without any further re-enqueue. This is bounded and intended.
6. `WorkItemKey` and the queue's single-flight and coalescing semantics are
   unchanged. Per item and image surface at most one work item is in flight.
7. The bounded post-save trigger still enqueues new-version hints for all
   eligible items; this decision only ensures the hint it lost to coalescing is
   not lost to the operator in the in-flight and pending cases.
8. The re-enqueue carries no secret, path, or provider payload; it is the same
   bounded hint the existing triggers enqueue, and the discard classification is
   a bounded, non-secret enum.

### Consequences

- Immediately after a settings change, an item whose work happened to be pending
  or in flight at save time is re-rendered rather than waiting for the next
  unrelated trigger.
- The fix is localized to the work-processing/discard boundary plus the release
  ordering in the worker; the queue key and single-flight contract are
  preserved.
- A configuration save can cause one additional bounded work item per affected
  subject; the bound is `QueueCapacity` as for any other trigger.
- An item that became ineligible while the old-version work was outstanding
  receives one extra bounded processing attempt before it is discarded for its
  real reason.
- No output or render fingerprint changes; this is a scheduling decision, not an
  output-affecting one.

### Rejected alternatives

- **Version-aware `WorkItemKey`.** Rejected: it changes the coalescing identity
  and can admit duplicate concurrent work for one item/surface.
- **Upgrade the pending item on coalesce only.** Rejected on its own: it cannot
  upgrade work that is already in flight, so the in-flight case would remain
  broken.
- **Re-enqueue from inside the processing path.** Rejected: the same-key enqueue
  is coalesced while the key is in flight, so the fix would be silently lost.
- **Have the worker compare `item.ConfigurationVersion` to the current version.**
  Rejected: the worker would then also re-enqueue on successful-but-stale work,
  which is broader than this decision; the classification must come from the
  processor.
- **Rely on a later trigger.** Rejected: it is the documented limitation this
  decision removes.
