# ADR-025: Read-Only Diagnostics Status Surface

**Status:** Accepted (v1.2). This extends ADR-016's dashboard settings surface and
amends the open-limitation clause of `docs/architecture/12-performance-and-operational-limits.md`.

**Date:** 2026-09-25

### Context

Queue depth, provider health, matching, cache, rendering, and stale-metadata
counters exist internally, but there is no bounded, secret-free user-facing or
diagnostic status surface. Architecture section 12 states that metrics or
diagnostic status should distinguish queue depth, API health, matching failures,
cache hits/misses, render failures, and stale metadata without exposing
credentials or full external payloads, and records the surface as an open
limitation (F3). ADR-020 clause 7 states that logging is a diagnostic mechanism,
not a metrics/status surface, so F3 cannot be satisfied by raising verbosity.

The supported Jellyfin 12 contract for a plugin route is a plugin `ControllerBase`
discovered through `ApplicationHost.GetApiPluginAssemblies`
(`docs/research/jellyfin-12-architecture.md` section 2.2). The
administrator-gating pattern is `[Authorize(Policy = Policies.RequiresElevation)]`
(section 9.3). ADR-016 already provides the embedded settings page as the
existing operator surface.

### Decision

ArrTags adds a read-only diagnostics status surface: a new admin-authenticated
plugin endpoint plus a read-only panel on the existing ArrTags settings page.

1. **Endpoint.** A new plugin API controller exposes one read-only route (for
   example `GET /ArrTags/Status`) gated by
   `[Authorize(Policy = Policies.RequiresElevation)]`, so only an authenticated
   administrator can read it. It is read-only: it never mutates configuration,
   work, or artwork, and it adds no write route. This is a distinct, v1.2
   read-only surface; it is not a reopening of the v1.1 decision that rejected a
   plugin-owned status endpoint as an inline configuration-rejection mechanism.
   ADR-016 clauses 3 and 4 forbid a custom configuration-save route, not a
   read-only, elevation-gated read route.
2. **Panel.** The read-only diagnostics panel is added to the existing embedded
   `Configuration/config.html` page. That page resource is served anonymously
   (ADR-016 clause 6) and is static HTML/JS only; the panel's data comes solely
   from the elevation-gated endpoint. When the endpoint is not authorized or
   unavailable, the panel renders no data (fail-closed, no data and no error
   surface); it never renders a secret and contains no secret literal.
3. **Bounded counters.** The endpoint returns a bounded, secret-free snapshot
   with a fixed counter set: update-queue depth and in-flight work; provider
   connection health; matching failures; cache hits and misses; render failures
   (by bounded classification); and stale-metadata counts. The listed set is the
   fixed minimum shape; adding or removing a counter requires a new decision,
   because the response shape is a contract the panel and its tests depend on.
   Each value is a count or a bounded enum, never a path, item name, item
   identifier list, provider payload, credential, `SecretLease` value, or
   unbounded collection.
4. **Bounded shape.** The response is a fixed-shape record with a bounded number
   of fields and no per-item array; it never serializes a whole library, a work
   queue, or a provider inventory. Counters are derived from existing bounded
   sources; where a counter does not exist, a bounded process-lifetime counter is
   added rather than retaining per-item history.
5. **No new configuration.** The surface adds no user-configurable setting. The
   anonymous static page-resource acceptance of ADR-016 clause 6 is unchanged;
   the status data is behind elevation.
6. **Security review.** The endpoint and panel are a new administrator-visible
   surface and require a fresh security review of authorization, secret-freedom,
   and bounded payload.

### Consequences

- Operators gain a supported in-product view of queue depth, provider health,
  matching, cache, rendering, and stale metadata without reading host logs.
- A new elevation-gated endpoint is added; it must remain read-only, secret-free,
  and bounded. Its panel renders no data when the endpoint is not authorized
  (fail-closed), so an anonymous page view never exposes status data.
- The surface is distinct from the v1.1 inline configuration-rejection decision:
  it is a read-only, elevation-gated read route, not a status endpoint used as a
  configuration-rejection mechanism, and the save path is unchanged.
- Process-lifetime counters reset on restart; the surface reports current
  process state, not durable history.
- F3 can be recorded as resolved once the surface ships and is reviewed.

### Rejected alternatives

- **Raise log verbosity instead.** Rejected: ADR-020 clause 7 explicitly scopes
  logging as a diagnostic mechanism, not a status surface.
- **A separate dashboard page.** Rejected: the user-accepted decision places a
  read-only panel on the existing settings page, avoiding a second page and a
  second navigation surface.
- **An anonymous or non-elevated endpoint.** Rejected: status counts are
  administrator-relevant and the supported admin pattern is elevation-gated.
- **A per-item diagnostic listing.** Rejected: unbounded payload and a potential
  path/metadata exposure.
