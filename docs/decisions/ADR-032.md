# ADR-032: Restoration Verification Semantics

**Status:** Accepted (v1.3). This refines the restoration postcondition recorded
by ADR-002 and ADR-003. The concrete equivalence rule is selected by DG-25 against
a `jellyfin-expert` verification spike; this ADR fixes the shape of the decision,
not the predicate.

**Date:** 2026-10-01

### Context

After writing the retained source baseline back to a subject, `ArtworkPublisher`
verifies the result by comparing Jellyfin's read-back of the surface against the
retained artifact:

```csharp
// src/ArrTags/Artwork/ArtworkPublisher.cs:936-946
return observedAfter.Presence == ArtworkImagePresence.Present
    && operation.CandidateAfterContentSha256 is not null
    && string.Equals(observedAfter.ContentSha256, operation.CandidateAfterContentSha256,
                     StringComparison.OrdinalIgnoreCase);
```

`CandidateAfterContentSha256` is the retained artifact id, that is, the SHA-256 of
the exact bytes ArrTags uploaded (set at `ArtworkPublisher.cs:659` from
`state.SourceArtifactId`). A mismatch is fail-closed and terminal:
`WriteRestoreBlocked` records `RestoreBlocked` (`:818-819`).

This demands that the host's `SaveImage` → ArrTags read-back path be
**byte-preserving**. Two facts make that an unexamined assumption rather than a
verified property:

1. The predicate is inherited by analogy from the publication path rather than
   derived from a measurement. 650+ subjects have published successfully against
   the pinned host, which is evidence that the publication comparison passes in
   practice — but the artifacts involved were captured from the same host and the
   comparison is a hash of a hash round-trip that this session did not isolate.
2. The host is a general image pipeline. Nothing in ArrTags' contract, ADR-015, or
   the pinned-host documentation asserts that `IProviderManager.SaveImage` stores
   the uploaded bytes verbatim rather than re-encoding, re-tagging, or
   re-containerizing them. A JPEG re-encoded at a different quality, or an image
   whose container is normalized, changes the SHA while remaining visually
   identical.

If the host is not byte-preserving, the failure mode is severe and identical in
shape to ADR-030's: the restore is attempted, the visual result is correct, the
verification disagrees on bytes alone, and the subject is sealed in
`RestoreBlocked` with no in-product remedy in v1.2.

**This is recorded as an unverified assumption, not as a defect.** The origin
session observed the *cancellation* path (ADR-030), not a byte-mismatch path: the
affected operation record carried `LastError: "The restoration mutation was
cancelled."` with `ObservedAfter: null`, so no read-back comparison was ever
reached. No open limitation is registered for a mismatch that has not been
observed. If DG-25 establishes that the host normalizes image bytes, a new open
limitation is registered at that point with the spike's evidence.

### Decision

1. **Verify before assuming.** Before the predicate changes, a `jellyfin-expert`
   spike measures, against the pinned Jellyfin 12 host, whether `SaveImage`
   followed by the ArrTags image read-back returns byte-identical bytes for both a
   JPEG and a PNG source, and records what the host does to image bytes on save.
   This is a Task Conformance Precondition under `docs/agent-contracts.md`: it
   runs before the predicate is implemented, not after.
2. **The predicate is derived from the measurement.** If the host is
   byte-preserving for the supported formats, the predicate stays
   content-SHA-exact and the spike result is recorded as the evidence that settles
   the question. If it is not, the predicate adopts a documented, content-derived
   equivalence rule that cannot accept a visually different image.
3. **The equivalence rule is content-derived and bounded.** Any adopted rule is
   computed from decoded image properties (for example oriented dimensions and a
   decoded-pixel digest), never from a path, a file name, a modification time, or
   a host-supplied tag. It must be deterministic for a given image, must not depend
   on library size, and must be recorded in the render/artwork documentation as
   part of the restoration postcondition.
4. **Fail-closed is preserved.** An unobservable read-back, a presence mismatch, a
   byte mismatch under a byte-exact predicate, and a failure of the adopted
   equivalence rule all remain non-mutating, classified outcomes. No equivalence
   rule may resolve a difference to "close enough"; the rule exists only to
   tolerate a host normalization that is proven not to change image content.
5. **The same predicate governs publication and restoration.** The publication
   postcondition is reviewed against the spike result at the same time, so the two
   paths cannot diverge into different notions of "the same image".
6. **No fingerprint change.** The restoration postcondition is a safety check, not
   an output-affecting input; no `RenderVersion` advance and no render-fingerprint
   change is required by this ADR.

### Consequences

- The restoration postcondition rests on a recorded measurement rather than an
  assumption, and the residual risk of sealing a visually correct restore is
  either closed or bounded by a documented rule.
- If the host proves byte-preserving, v1.3 ships a spike note and a test and no
  behavior change.
- If it does not, adoption of a content-derived rule widens what ArrTags treats as
  "the same image" for the restoration postcondition only. The rule is proven
  content-derived, so it does not weaken the ownership comparison in ADR-002, which
  is a separate decision and is not amended here.
- The spike adds a research dependency to Phase 24, which is why G12 is ordered
  after the G10 and G11 phases rather than alongside them.

### Rejected alternatives

- **Keep the byte-exact predicate and record the assumption as accepted.**
  Rejected: the cost of being wrong is a permanently stranded poster with no
  v1.2 remedy, and the measurement is cheap against the pinned host.
- **Drop verification and trust the write.** Rejected: verification is the
  fail-closed guarantee that ArrTags never claims artwork it did not write.
- **Compare file modification time or a host image tag instead of content.**
  Rejected: neither is content-derived, and `V12-F7-1` already records that
  re-adoption of a host image desynchronises the served image from the recorded
  identity. ADR-030 leaves the ownership comparison's use of those fields
  unchanged and out of scope here.
- **Accept any read-back of the right presence and dimensions.** Rejected: that
  would accept a visually different image and defeat the purpose of verification.
