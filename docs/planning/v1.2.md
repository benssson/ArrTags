# ArrTags v1.2 Plan

**Status:** Accepted. No v1.2 behavior is implemented by this document yet. The
v1.2 plan and its decision records ADR-022 through ADR-028 are accepted
(`Accepted (v1.2)`); decision gates DG-19, DG-20, and DG-21 are resolved by this
plan and their ADRs, so no dependent implementation task remains gated on a
pending decision.

**Date:** 2026-09-25

**Purpose:** Define the v1.2 scope, goals, decision gates, dependency order, and
task outline for ArrTags. This document is the governing scope for v1.2; the V1
documents (`GOALS.md`, `docs/architecture/`, `docs/data-model/`,
`docs/decisions/`) remain authoritative for V1 and v1.1 until a v1.2 ADR
explicitly supersedes a named clause. Prior history is not rewritten.

## 2. Goals

### Goal G6 — Expose byte settings in MB

**Value:** Operators read and edit byte-denominated limits in familiar binary
units instead of raw byte counts.

**Current state:** `OperationalLimits` stores and validates bytes, and
`Configuration/config.html` shows raw byte counts with byte validation ranges for
`ProviderResponseLimitBytes`, `WebhookMaxPayloadBytes`,
`SourceArtifactLimitBytes`, `DerivedArtifactLimitBytes`, `RenderCacheQuotaBytes`,
`ArtifactStorageQuotaBytes`, and `InventoryCacheMaxBytes`.

**Decision:** `ADR-028` (Accepted, v1.2). A fixed binary unit per field (MB for
every byte limit, KB for `WebhookMaxPayloadBytes`), with a per-field step and
display precision that make the minimum, default, and maximum exact (including
the 64 KiB minima); internal/persisted values stay bytes; exact round-trip at
minimum, default, and maximum.

**Acceptance criteria:**

- Byte-denominated limits are displayed in a fixed binary unit chosen per field
  (MB, except the webhook payload limit in KB), with validation ranges shown in
  the same unit and precision; a range that spans 1 MiB stays in the field's unit
  and shows the sub-1-MiB bound as a fraction.
- Display -> store -> display and store -> display -> store round-trips preserve
  the exact byte value at minimum, default, and maximum for every byte-denominated
  limit, including the 64 KiB minima of `ProviderResponseLimitBytes`,
  `SourceArtifactLimitBytes`, and `DerivedArtifactLimitBytes`.
- A value that does not land on the field's fixed step (for example `0.1 MB` for
  a 64 KiB-step field) is rejected by an **explicit step-multiple check** owned by
  task 16.1; the existing `OperationalLimits.Validate` range check alone does not
  enforce step alignment, so the new check is required in the settings
  conversion/validation path (and, where native constraint validation is used,
  the input's `step` attribute).
- The persisted XML representation and the internal `OperationalLimits` values
  remain bytes; an existing `ArrTags.xml` loads unchanged.

### Goal G7 — Extra Large badge size and size ordering

**Value:** Operators can render a larger badge, with a predictable size order in
the settings UI.

**Current state:** `BadgeSize` has `Medium = 0`, `Small = 1`, `Large = 2`;
`BadgeGeometry.SizeFactor` returns `0.75`, `1.0`, and `1.5`; the settings
dropdown offers Medium, Small, Large.

**Decision:** `ADR-027` (Accepted, v1.2). Add `BadgeSize.ExtraLarge = 3` with
factor `2.0`, order the dropdown Small, Medium, Large, Extra Large, clamp the
effective scale to the safe area, do not advance `RenderVersion` or the renderer
configuration schema, and add golden coverage while keeping existing goldens
byte-identical.

**Acceptance criteria:**

- `BadgeSize.ExtraLarge` exists with a `2.0` factor relative to Medium; the
  `BadgeGeometry.SizeFactor` switch and the `RendererConfiguration` validation
  coverage are extended for the new value; the effective scale is still clamped so
  no badge paints outside the safe area.
- The settings dropdown order is Small, Medium, Large, Extra Large.
- Existing Small/Medium/Large renders are unchanged and their committed goldens
  are byte-identical; new Extra Large goldens are added and deterministic.
- The renderer configuration and render fingerprints include a non-default size,
  so selecting Extra Large republishes only the selecting items.

### Goal G8 — Restart-required note text and modal reminder

**Value:** Operators can tell which saved settings apply immediately and which
need a host restart, so a saved change is not mistaken for ineffective.

**Current state:** Some services resolve limits from the current snapshot per
operation, while some singletons capture artifact-size/decode and
`StateRepository`-backed TTL/quota/retention values at construction (ADR-016
implementation note; architecture section 6). The settings page gives no restart
indication.

**Decision:** `ADR-028` (Accepted, v1.2). Produce the authoritative,
code-evidenced restart-required set; always show note text on restart-required
settings; show a modal reminder on change where the jellyfin-web modal API
supports it, with the note text as the fail-open behavior.

**Acceptance criteria:**

- The authoritative restart-required set is recorded with per-setting code
  evidence and is testable (a code-owned classification); a setting with both a
  construction-captured and a per-operation consumer is classified
  restart-required, and its note text states that some paths apply immediately.
- Every restart-required setting in the settings page carries note text stating
  that a server restart is required.
- A changed restart-required setting triggers the modal reminder when the modal
  API is available; when it is not, the note text remains and the save behavior
  is unchanged.
- A `jellyfin-expert` research spike records the modal API's availability and
  stability before the modal is implemented.

### Goal G9 — Log file name instead of item id

**Value:** Log lines identify the media file directly, so an operator can
correlate artwork and matching events without a second lookup.

**Current state:** The artwork coordinator, the metadata reconciliation processor,
the Sonarr/Radarr metadata readers, the work worker, and the lifecycle service
emit the Jellyfin item id; some of those sites hold a `MediaIdentity` with
`MediaLocation.PrimaryPath`.

**Decision:** `ADR-026` (Accepted, v1.2), amending ADR-020 clause 4 by adding the
bounded log subject to the allowed redacted-value set and adding an explicit
directory/full-path exclusion. Emit a bounded file-name-only log subject when a
path is available, falling back to the item id when it is not; never emit a
directory or path; require a fresh security review.

**Acceptance criteria:**

- The identity-bearing sites (artwork coordinator, the metadata reconciliation
  processor's metadata-read-failure line, and the Sonarr/Radarr metadata readers)
  emit the file name component only when a path is available; the mixed
  `MetadataReconciliationProcessor.Discard` site uses the file name when a path
  is available and falls back to the item id otherwise; the fallback sites (work
  worker, lifecycle removal event) emit the item id explicitly.
- The file name is bounded, control characters are stripped, and an empty or
  whitespace name falls back to the item id.
- No directory, drive, share, full path, credential, or secret appears in the
  log output; redaction tests cover the new subject at every verbosity level.
- ADR-020 clause 4 is amended and the log path is security-reviewed.

### Goal F3 — Bounded, secret-free diagnostics status surface

**Value:** Operators get a supported in-product view of queue depth, provider
health, matching, cache, render, and stale-metadata state without reading host
logs.

**Current state:** The counters exist internally but there is no bounded,
secret-free status surface (limitation F3).

**Decision:** `ADR-025` (Accepted, v1.2). A read-only diagnostics panel on the
existing ArrTags settings page, backed by a new plugin endpoint gated by
`[Authorize(Policy = Policies.RequiresElevation)]`, returning a bounded,
secret-free snapshot.

**Acceptance criteria:**

- A plugin endpoint returns a bounded, secret-free diagnostics snapshot and is
  authorized only for an authenticated administrator (host-guarded confirmation).
- The existing ArrTags settings page shows a read-only panel rendering the
  counters: queue depth/in-flight, provider health, matching failures, cache
  hits/misses, render failures, and stale metadata.
- The endpoint is read-only, adds no write route, exposes no secret, path, item
  name, provider payload, or unbounded collection, and has a fixed bounded shape.
- The endpoint and panel are security-reviewed.

### Goal F4 — Reconciliation coverage across successive runs

**Value:** A scope larger than `QueueCapacity` is eventually fully covered instead
of the same prefix being re-covered.

**Current state:** Scheduled and post-scan reconciliation enumerate from the
start of a deterministic order; the bounded queue drops overflow; successive runs
overlap (limitation F4). Event, webhook, and per-item triggers are unaffected.

**Decision:** `ADR-022` (Accepted, v1.2). A persisted, bounded reconciliation
cursor advances across successive runs over the deterministic order and wraps at
the end; the cursor resets on a scope change; scheduled and post-scan only. The
enqueue boundary gains a bounded outcome vocabulary so a coalesced or in-flight
item is covered without stalling the run and an overflow stops it at the first
uncovered item; the cursor is a stable `(SortName, itemId)` seek key rather than
an integer offset.

**Acceptance criteria:**

- Successive scheduled/post-scan runs over a scope larger than `QueueCapacity`
  cover the whole scope over time (round-robin), with one run still bounded; a
  coalesced or in-flight item does not stall the run, and the run stops at the
  first overflow without re-covering the prefix.
- The cursor is a bounded, versioned, secret-free `Cache`-authority state record
  with a stable `(SortName, itemId)` position; it resets on an
  enabled-library/item-type scope change and on a missing/torn/out-of-range
  cursor.
- Event, webhook, per-item, and post-save triggers do not read or write the
  cursor and are unchanged.
- Coverage tests prove whole-scope coverage across successive runs, including the
  coalesce, in-flight, overflow-stop, and library-mutation cases.

### Goal F6 — Version-aware post-save re-render

**Value:** A settings save re-renders an item whose work happened to be pending
or in flight at save time, instead of dropping the new-version hint.

**Current state:** The version-blind queue key coalesces the post-save
new-version hint away and the outstanding item discards itself as a stale basis
without re-enqueueing (limitation F6).

**Decision:** `ADR-023` (Accepted, v1.2). Re-enqueue exactly one fresh work item
at the current configuration version when a work item completes with the
`ConfigurationStale` discard classification, bounded to one per (item,
connection, surface, version); the re-enqueue happens after the in-flight slot is
released; `WorkItemKey` and single-flight are unchanged.

**Acceptance criteria:**

- A work item that discards with the `ConfigurationStale` classification
  re-enqueues one work item at the current version after the in-flight slot is
  released; the item re-renders without waiting for an unrelated trigger, and no
  re-enqueue is silently coalesced away.
- The re-enqueue is bounded and cannot loop: the fresh item carries the current
  version, so a same-version discard does not recur, and a stopped or full queue
  drops the re-enqueue. A discard with any other classification (`ItemMissing`,
  `Ineligible`, `ConnectionChanged`, `IdentityUnavailable`) does not re-enqueue.
- An item that became ineligible or absent while old-version work was outstanding
  is re-enqueued once and then discarded for its real reason without further
  re-enqueue.
- `WorkItemKey` remains version-blind and single-flight per item/surface is
  preserved; event, webhook, and per-item triggers are unchanged.
- Coalescing coverage tests prove the post-save case and fail if the re-enqueue
  is issued before the in-flight slot is released; a test proves a non-version
  discard does not re-enqueue.

### Goal F7 — Empty-selection artwork restoration

**Value:** Narrowing a selector allowlist removes or restores a stale ArrTags
badge instead of leaving a badge that contradicts the configuration.

**Current state:** A `NoDisplayableValue` pass-through preserves the previous
ArrTags badge indefinitely; restoration runs only on item removal or the
lifecycle drain (limitation F7).

**Decision:** `ADR-024` (Accepted, v1.2). An **empty resolved selection** on an
owned session restores the retained source baseline, or removes the ArrTags image
when no baseline existed, through the existing guarded restore/removal protocol
(the internal `ArtworkPublisher.RestoreAsync` under the current Normal fence and
the existing subject gate); the other pass-through reasons keep preserving the
current artwork, including a non-empty selection that cannot fit (`NoFittingBadge`).

**Acceptance criteria:**

- An owned session that resolves an empty selection (the now-unambiguous
  `NoDisplayableValue` reason) restores the retained source baseline, or removes
  the ArrTags image when the baseline was absent, through the crash-recoverable
  protocol and the internal `ArtworkPublisher.RestoreAsync` entry point.
- The other pass-through reasons (`NoMetadata`, `NoFittingBadge`,
  `IneligibleSurface`, `MatchNotEligible`, `SourceUnavailable`) preserve the
  current artwork and perform no image mutation; a non-empty selection that
  cannot fit the safe area performs no mutation.
- A non-owned session with an empty selection remains a pass-through; ArrTags
  never mutates artwork it does not own.
- Restoration uses the existing crash-recoverable operation protocol and is
  resumed on restart by the ordinary recovery gate; ADR-009 and ADR-002/ADR-003
  amendment notes are recorded and coverage tests pass.
- The absent-baseline removal case is exercised by a direct publisher test with a
  synthetic persisted `Published` state that has no retained baseline (the
  coordinator path returns `NoSource` before publishing, so this branch is not
  reachable through the normal generation path).

### Goal F8 — Render classification in the artwork log

**Value:** The specific bounded render classification is visible, so two
different no-badge causes are distinguishable without reproducing with tests.

**Current state:** The artwork log emits only the outcome and the generic reason;
the bounded `PassThroughReason`, `FailureReason`, and `SourceFailureReason` are
retained on the result but not emitted (limitation F8).

**Decision:** No ADR. Emit the bounded classification in the existing
artwork-boundary log line; the classifications are bounded enums, so this is
compatible with the ADR-020 clause 4 redaction contract (as amended by ADR-026).

**Acceptance criteria:**

- The artwork log line emits the specific bounded classification when present
  (`PassThroughReason`, `FailureReason`, or `SourceFailureReason`).
- The classifications remain bounded and secret-free; redaction tests cover them.
- The change is compatible with ADR-020 clause 4 as amended by ADR-026.

## 5. Dependency order

1. **Goal G9 + F8 (ADR-026)** first. Logging is cross-cutting: it amends the
   ADR-020 clause 4 security contract and edits the artwork log line that F8 also
   changes, so the two ship together in one phase.
2. **Goals G6 + G8 (ADR-028)** next. They share the settings page's operational
   limits section and the restart-required classification; G8 also needs the
   settings page before F3's panel can be added.
3. **Goal F3 (ADR-025)** next. It adds the endpoint and the read-only panel to
   the settings page delivered by the previous phase, and owns its own security
   review.
4. **Goal G7 (ADR-027)** next. It is output-affecting (new goldens) and
   independent of the settings/logging work.
5. **Goals F4 + F6 (ADR-022, ADR-023)** next. Both are reconciliation/queue
   behavior and touch the same components; their mechanism choices are decision
   gates.
6. **Goal F7 (ADR-024)** next. It is the artwork pass-through/restoration change
   and is independent of the reconciliation work.
7. **Release (version bump, build/package, live verification, release security
   review, release review)** last.
