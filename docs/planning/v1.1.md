# ArrTags v1.1 Plan

**Status:** Accepted for planning. No v1.1 behavior is implemented by this document yet.

**Date:** 2026-09-23

**Purpose:** Define the v1.1 scope, goals, decision gates, dependency order, and
task outline for ArrTags. This document is the governing scope for v1.1; the V1
documents (`GOALS.md`, `docs/architecture.md`, `docs/data-model.md`,
`docs/decisions.md`) remain authoritative for V1 until a v1.1 ADR explicitly
supersedes a named clause. V1 history is not rewritten.

## 1. Relationship to V1

- `GOALS.md` continues to govern the V1 in-scope/out-of-scope lists. v1.1 goals
  are additive and are defined here.
- `docs/architecture.md` and `docs/data-model.md` are updated in place as v1.1
  decisions land, with the changes described in the v1.1 ADRs.
- `docs/limitations.md` is the canonical "not done / not verified" register.
  Items F1 and F2 are promoted to v1.1 by this plan; other V1 limitations remain.
- New decisions are recorded as `ADR-016` onward in `docs/decisions.md`.
- V1 documentation conventions (per-task reports under `docs/implementation/`,
  evidence in `docs/research/`, live matrix in
  `docs/testing/jellyfin-12-musl-test-host.md`) continue to apply.
- **Release identity:** v1.1 is version `1.1.0.0`; the release tag is `v1.1.0`
  and phase tags use `v1.1.0-phase<N>` (for example `v1.1.0-phase9`), continuing
  the V1 convention (`v0.1.0-phase<N>` for phases, `v<version>` for a release).

## 2. Goals

### Goal A — Dashboard settings UI

**Value:** Configure ArrTags from the Jellyfin dashboard instead of editing
`plugins/configurations/ArrTags.xml` and restarting.

**Current state:** `README.md` states there is no web configuration UI. The
configuration is read only at startup, so a saved change is not observed until
the process restarts (`docs/limitations.md` F2).

**Decision:** `ADR-016` (Accepted). Confirmed supported contracts are in
`docs/research/jellyfin-12-architecture.md` §9.

**Acceptance criteria:**

- A plugin settings page appears in the Jellyfin dashboard and loads its current
  configuration.
- Saving a valid change applies it at runtime without a host restart; an invalid
  change is rejected and the last valid snapshot is retained.
- A successful save triggers a bounded reconciliation so affected posters
  re-render with the new settings instead of waiting for the next scheduled run.
- No secret is embedded in the page or returned beyond Jellyfin's existing
  admin configuration behavior.
- Configuration is saved only through the elevation-gated supported path.

### Goal B — Badge value allowlist

**Value:** Render a badge only for a selected whitelist of values, so operators
can suppress unwanted values without disabling the whole selector.

**Current state:** Selectors can be enabled/disabled and templated
(`RendererConfiguration`), but there is no per-value filter.

**Decision:** `ADR-017` (Accepted): a per-selector allowlist with
case-insensitive exact matching against the resolved pre-template value, bounded
and validated, included in the renderer configuration fingerprint.

**Acceptance criteria:**

- A configured allowlist restricts rendering to the listed values.
- The allowlist is bounded, validated at configuration load, and secret-free.
- Unknown/absent values remain omitted; an empty allowlist means "no
  restriction".
- The change is output-affecting: renderer configuration fingerprint changes and
  `RenderVersion` advances.

### Goal C — Provider inventory cache and library-refresh-driven refresh

**Value:** Stop re-reading the whole provider library for every reconciliation
work item.

**Current state:** `docs/limitations.md` F1 — each work item re-reads
`/api/v3/movie` or `/api/v3/series` and the per-record file resource. The
`GOALS.md` "avoid unnecessary API requests" goal is only partially met for
provider fetches.

**Correction of an earlier assumption:** badges are **not** rendered per poster
request. Per ADR-001, badges are published as persisted Jellyfin item images and
served by Jellyfin's normal image routes, so no Arr call happens per request. The
problem is reconciliation fetch volume, not request-time caching.

**Decision:** `ADR-018` (Accepted). Evidence: `docs/research/sonarr-api.md` and
`docs/research/radarr-api.md` ("Conditional requests and inventory caching").

**Acceptance criteria:**

- One provider library read per connection serves a reconciliation window
  instead of one read per work item.
- Invalidation is ArrTags-side (webhook, Jellyfin library refresh/post-scan,
  scheduled/manual reconciliation, bounded TTL); no provider conditional
  request, revision token, or SignalR dependency.
- The cache is bounded and secret-free, with validated TTL/size limits.
- Provider failure keeps the existing bounded last-known-good behavior.

### Goal D — README palette documentation gap

**Value:** Explain the palette override fields that `README.md` currently names
but never documents.

**Current state:** `README.md` references `TechnicalBackground`, `TechnicalText`,
`StatusBackground`, and `StatusText` as "optional palette overrides (see below)"
but the promised explanation does not exist.

**Decision:** No ADR. A documentation fix bundled into the v1.1 README pass.

**Acceptance criteria:**

- The four fields are documented with their meaning, default colors, and the
  4.5:1 contrast rule.

### Goal E — Badge size and position options

**Value:** Choose the rendered badge size and place it in a corner or the center.

**Current state:** ADR-009/ADR-010 fix geometry and placement as code-owned and
explicitly not representable in configuration; the technical rail is
bottom-left and the status pill is top-right.

**Decision:** `ADR-019` (Accepted; supersedes the code-owned geometry/placement
clauses of ADR-009/ADR-010): a global `BadgePosition` (four corners plus center)
and a preset `BadgeSize` (Small/Medium/Large).

**Acceptance criteria:**

- A configured size and anchor (four corners plus center) affect the rendered
  badge.
- Rail packing, status-pill placement, and safe-area bounds are defined per
  anchor; no badge paints outside the safe area.
- The change is output-affecting: fingerprint changes, `RenderVersion` advances,
  and goldens are regenerated.

### Goal F — Logging with configurable verbosity

**Value:** Operators can diagnose ArrTags behavior and change its verbosity
without changing the global Jellyfin log level.

**Current state:** The plugin has zero logging call sites; `docs/limitations.md`
SEC-5 relies on that to assert no plugin log path can leak a secret.

**Decision:** `ADR-020` (Accepted). Evidence:
`docs/research/jellyfin-12-architecture.md` §10.

**Acceptance criteria:**

- The plugin logs through the host logging pipeline at a configurable verbosity.
- Verbosity is bounded, validated, secret-free, and applied without restart (via
  Goal A).
- Every log call is secret-free; redaction is covered by tests at every level.
- Verbosity does not affect rendered output or output fingerprints.
- SEC-5 is rewritten and the logging path is security-reviewed.

## 5. Dependency order

1. **Goal A (ADR-016)** first. It is the delivery vehicle for the new settings
   exposed by Goals B, E, and F, and it resolves F2.
2. **Goal F (ADR-020)** early. It is cross-cutting and rewrites a documented
   security claim (SEC-5).
3. **Goal C (ADR-018)** independent; it shares the runtime-configuration
   plumbing introduced by Goal A.
4. **Goals B (ADR-017) and E (ADR-019)** last. Both are output-affecting and
   require a fingerprint change, a `RenderVersion` bump, and golden
   regeneration.
5. **Goal D** rides in the README/documentation pass.

## 9. Verification requirements

- Unit/integration tests for each task, including: configuration round-trip
  (get-only collections), runtime activation and last-valid retention, redaction
  at every verbosity, cache invalidation and bounds, allowlist behavior, and
  placement/size geometry.
- Golden regeneration and byte-determinism for the output-affecting changes
  (Goals B and E), with `RenderVersion` advanced.
- A fresh security review covering the new logging path and SEC-5 rewrite, and
  the ADR-016 settings page and administrator save path.
- Live verification on the pinned Jellyfin `12.0.0` host
  (`docs/testing/jellyfin-12-musl-test-host.md`): settings page load/save,
  post-save re-render, cache behavior, and log output/level.
- Reproducible build/package at the v1.1 version (`1.1.0.0`).

## 10. Out of scope

- The bounded metrics/diagnostic-status surface (`docs/limitations.md` F3)
  remains open and separate from logging.
- All V1 deliberate exclusions in `GOALS.md` and `docs/limitations.md`
  (Jellyfin versions before 12, modifying media files, Arr write operations,
  non-poster artwork, user-specific badges, unapproved services, path fallback)
  remain out of scope unless separately decided.
