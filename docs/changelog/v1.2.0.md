## Phase 15 - Plugin log subject identifier and render classification (v1.2)

### Task 15.1 - Bounded log-subject policy and helper

**Status:** Complete. Owns ADR-026 clauses 1-2 (G9); the clause 3 threading is
task 15.2.

`src/ArrTags/Logging/LogSubject.cs` is the shared bounded log-subject helper.
`LogSubject.Create(Guid jellyfinItemId, string? primaryPath)` returns the
file-name component only (`Path.GetFileName`), never a directory, drive, share,
or parent path, and falls back to the Jellyfin item identifier in `D` format
whenever no usable name is available; `LogSubject.Create(Guid jellyfinItemId)`
is the item-id-only overload for the explicit fallback sites. The file name is
bounded to the documented `LogSubject.MaximumScalarValues` (128 Unicode scalar
values), has control scalars removed, and is otherwise emitted verbatim
(whitespace is not collapsed or trimmed), all in a single scalar-wise pass so a
surrogate pair is never split. An empty, whitespace, or control-only name — and
a name that reduces to whitespace-only text after normalization, for example
`" \u0001 "` — falls back to the item identifier. The helper never throws for a
null, empty, whitespace, or otherwise unusable path.

documented bound (exactly-at-bound unchanged, over-bound truncated, a surrogate

whitespace collapsing, non-ASCII and combining text emitted verbatim,
empty/whitespace and control-reduced fallback, and the `D`-format
item-identifier fallback. Test sensitivity was probed by temporarily removing
each behaviour (path splitting, the scalar bound, control removal, the
post-normalization fallback check, and the `D` fallback format): the
corresponding cases failed and every probe was reverted.

### Task 15.3 - Emit the bounded render classification in the artwork log

**Status:** Complete. Owns the code half of F8; the ADR-020 clause 4 amendment,
the canonical documentation (README/architecture/limitations), the logging
security review, and the F8 resolution are task 15.4.

`ArtworkGenerationCoordinator.LogOutcome` now appends the specific bounded render
classification to the single artwork-boundary record when the result carries one.
A private `DescribeClassification` helper returns
` (PassThroughReason=<RenderPassThroughReason>)` for a pass-through result,
` (FailureReason=<RenderFailureReason>)` for a render failure,
` (SourceFailureReason=<ArtworkSourceReadFailureReason>)` for a source-read
failure, and an empty string otherwise, so the qualifier is placed between the
bounded outcome and the existing generic reason:

- `Artwork generation for item <subject> completed with RenderPassThrough (PassThroughReason=NoMetadata): The render passed through; the current artwork is preserved.`
- `Artwork generation for item <subject> completed with RenderFailed (FailureReason=DecodeFailed): The render failed; the current artwork is preserved.`
- `Artwork generation for item <subject> completed with SourceUnavailable (SourceFailureReason=Unreadable): The active source image could not be used.`

Each name is a bounded enum member (the same
`RenderPassThroughReason`/`RenderFailureReason`/`ArtworkSourceReadFailureReason`
values the result already carries), named by its enum kind so a pass-through, a
render failure, and a source-read failure with the same-looking cause stay
distinguishable. The helper emits fixed text plus the enum name only: no
exception message, provider payload, path, credential, or other unbounded value
is reachable from `ArtworkGenerationResult`. When the result carries no
classification (published, no source, blocked, cancelled, or
publication-not-completed), the empty qualifier leaves the record byte-identical
to the pre-task shape. `NoFittingBadge` is an ADR-024 reason owned by task 20.1
and is not added here.

## Phase 16 - Settings byte units and restart-required surfacing (v1.2)

### Task 16.1 - Byte/unit conversion helper and per-field MB/KB mapping (explicit off-step rejection)

**Status:** Complete. Owns ADR-028 clause 1 (G6) and the phase's explicit
step-multiple rejection. The restart-required set (16.2), the note text (16.3),
the modal spike and implementation (16.4/16.5), and the G6/G8 documentation and
integration verification sweep (16.6) are not part of this task.

`src/ArrTags/Configuration/ByteLimitField.cs` and
`src/ArrTags/Configuration/ByteLimitUnits.cs` are the code-owned ADR-028 display
mapping for the seven byte-denominated limits. Each field declares a fixed
binary unit (MB, `1 MB = 1048576 bytes`, except `WebhookMaxPayloadBytes` in KB,
`1 KB = 1024 bytes`), a fixed step `S` that divides its minimum, default, and
maximum, and a fixed display precision `P`: `S = 64 KiB` with `P = 4` for
`ProviderResponseLimitBytes`, `SourceArtifactLimitBytes`, and
`DerivedArtifactLimitBytes`; `S = 1 MiB` with `P = 0` for
`RenderCacheQuotaBytes`, `ArtifactStorageQuotaBytes`, and
`InventoryCacheMaxBytes`; and `S = 1 KiB` with `P = 0` for
`WebhookMaxPayloadBytes`. The field bounds equal the unchanged
`OperationalLimits.Validate` byte ranges and the property defaults, and a test
cross-checks each minimum, default, and maximum against the actual validation
behavior.

`ByteLimitField.FormatDisplay(bytes)` renders stored bytes at the field's
precision (`display = round(bytes * 10^P / U)`, trailing zeros trimmed, no unit
switch) and `FormatRange()` renders the unit-labelled range in the same unit and
precision, so a range that spans 1 MiB keeps the sub-1-MiB bound as an exact
fraction (`0.0625 - 64 MB`). `TryParseDisplay(text, out bytes)` accepts a plain
unsigned decimal with at most `P` fractional digits, parses it as a scaled
integer (scaled by `10^P`), computes `bytes = round(scaled * U / 10^P)`, and
rejects any value that is not an exact multiple of the field step rather than
rounding it (`0.1` MB for the 64-KiB-step fields computes 104858 bytes and is
rejected). The byte range is not re-checked by the conversion: it stays owned by
the unchanged `OperationalLimits.Validate` and the page's native input bounds.
The internal `OperationalLimits` values and the persisted `ArrTags.xml`
representation remain bytes; no endpoint or save route is added.

`src/ArrTags/Configuration/config.html` mirrors the mapping. The seven byte
inputs are `type="number"` with `min`, `max`, and `step` expressed in the field's
unit (`0.0625`/`64`/`0.0625` for the provider response limit), the
integer-only `pattern="[0-9]*"` is removed, the label names the unit, and a
`fieldDescription` shows the unit-labelled range. The inline JS declares the same
unit, unit bytes, step, and precision per field in `byteLimitFields`, displays
stored bytes through `byteLimitToDisplay`, converts a displayed value through
`byteLimitToBytes` (the same scaled-integer algorithm plus the explicit
`bytes % definition.stepBytes !== 0` rejection), rejects a non-step value in
`readByteLimitValues` before the save request with a native validity message,
and stores only the converted byte value into `config.Limits[...]`. The pageshow
path renders every stored value through the same mapping. The page is a static
embedded resource and this repository has no JS test runtime, so the page
contract is pinned by structural C# tests that compare the page table and the
native unit/step/range declarations against the C# mapping and that fail if the
submit path stops converting.

`tests/ArrTags.Tests/ByteLimitUnitsTests.cs` adds 103 cases: the seven-field
mapping, unit/step/precision per ADR-028, step-divisibility of every bound,
bounds/defaults cross-checked against `OperationalLimits.Validate`, the
unit-labelled range labels, exact display strings, store -> display -> store and
display -> store -> display round-trip at every minimum, default, and maximum
(including the 64 KiB minima `0.0625 MB`), the ADR `0.1` MB worked example, the
explicit off-step rejection, over-precision rejection, malformed input
rejection, and the unchanged load of a persisted off-step byte value through
validation, the snapshot service, and the XML boundary. `tests/ArrTags.Tests/ByteLimitSettingsPageTests.cs` adds 5 structural
cases: the page mapping table, the native min/max/step/unit per field, the
unit-labelled range label, the display/store conversion and the off-step check
ordered before the save request, and the absence of any raw-display write into a
byte field. Test sensitivity was probed by temporarily breaking each behavior:
removing the C# step check failed 8 cases; removing the trailing-zero trim
failed 9; breaking the provider step in the C# mapping failed 9 (mapping,
round-trip, step-multiple, and page-consistency cases); removing the page's step
check failed the conversion case; changing the page unit to `MB` for the webhook
field failed the mapping-table case; changing the provider `step` attribute
failed the native-attribute case; reverting the submit path to `parseInt` failed
both submit-path cases; changing a range label failed the range case; and adding
a temporary server-side step check to `PluginConfigurationValidator` failed the
persisted-off-step-value load case. Every probe was reverted.

An existing `ArrTags.xml` still loads unchanged and an off-step persisted value
(the pre-16.1 page accepted any in-range byte count) is displayed at the field's
fixed precision: when the rounded display value is itself a step multiple
(always the case for the whole-KiB and whole-MiB fields, where the display rounds
to a whole unit) a save writes that step multiple, and otherwise (the 64-KiB-step
MB fields) the save is rejected until the operator enters a step multiple. This
is the ADR-028 reject-rather-than-round behavior for values outside the
min/default/max round-trip guarantee.
